# 功能基线（baseline）

## 定义

功能基线验证当前代码自身的逻辑：在进程内直接调用被测代码，把网络、数据库、消息队列、外部 API、时钟、随机数等边界替换为可控的 test double。目标是快速、确定、可并行，并覆盖本次改动的所有分支。

文件系统默认使用内存 fake。只有当文件格式、路径或权限语义本身是契约时，才允许使用隔离临时目录；每个测试独立根目录、结束清理、不读写用户目录或共享状态，单例 ≤200ms。

## 覆盖矩阵

对每个改动点至少检查以下维度，只选适用的：

| 维度 | 要覆盖的情况 |
| --- | --- |
| 正常路径 | 典型输入得到预期输出或状态 |
| 边界值 | 最小/最大、空集合、长度为 0/1、临界阈值、时间边界 |
| 非法输入 | 类型错误、缺字段、越界、格式非法、权限不足 |
| 空值 | `null`/`None`/空字符串/空数组/未初始化 |
| 错误路径 | 依赖抛错、超时、部分失败、重试耗尽 |
| 状态转换 | 初始态、中间态、终态、重复调用、乱序调用 |
| 参数组合 | 开关组合、可选参数缺省、互斥参数 |
| 契约 | 返回值结构、序列化格式、错误码、副作用边界 |

并发、时序和重试只有在不依赖真实时间/调度的前提下才放进功能基线；否则归入场景测试或单独的压力/并发测试。

## test double 选择

- **stub**：只需要固定返回值或错误。
- **fake**：需要状态行为，例如内存仓库、内存队列、可控时钟。
- **mock/spy**：只在交互本身是契约时验证，例如必须调用一次审计接口。
- 不 mock 被测对象本身；不为每个内部函数建 mock。
- 优先在端口/边界注入依赖，而不是篡改模块内部实现。
- 时钟、随机数、UUID、环境变量通过参数或端口注入；测试内固定种子。

## 契约测试

- 契约：公开 API、schema、错误码、序列化格式、副作用边界。
- 按 import、调用点、API spec 找直接消费者；共享模块再取一跳传递消费者。
- 消费者契约测试放功能基线（mock 外部依赖）；provider 的真实集成验证放场景测试。
- 没有消费者测试时记录缺口并补最小契约用例；不要用全量场景测试代替契约测试。

## 结构

- 按模块组织：`tests/baseline/<module>/` 或与源码同目录的 `*.test.*`；runner 标记 `baseline`。
- 一个测试一个行为；名称写明条件与期望，例如 `rejects_expired_token`。
- 表驱动覆盖参数矩阵，避免复制粘贴多个近似用例。
- Arrange-Act-Assert 分段；失败信息包含输入、期望和实际。
- 测试之间不共享可变状态；需要共享 fixture 时只读或每次重建。

## 时长与测量

- 单个用例默认目标 200ms（runner 报告的 per-test duration，排除进程启动、编译和一次性 setup）。
- 超过 200ms 的纯代码用例进 `slow-baseline` 标记/套件，按模块按需运行，记录原因、预算和 owner，不计入 5 分钟默认；不得用它隐藏真实 I/O。
- 测量口径：依赖已安装、默认 worker 数、命令启动到退出的 wall-clock，包含收集和 fixture，不含依赖安装；记录机器/runner、commit、workers；取 3 次中位数。
- 全量功能基线 ≤5 分钟；按模块记录命令与耗时。
- 不用 `sleep` 等待异步；用可控时钟、事件或轮询上限明确的断言。

## slow-baseline

- 适用：纯代码、无真实依赖，但单例超过 200ms 的用例，例如大 fixture、复杂解析、property-based 测试。
- 运行：按模块按需，不进入默认全量；命令和预算记录在 `TESTING.md`。
- 禁止：把真实 I/O、网络、数据库用例放进 slow-baseline 冒充纯代码测试。

## 既有慢套件迁移

1. 用 `--durations`、`go test -json` 或 runner 报告找最慢用例。
2. 分类：真实 I/O → 场景测试；重复覆盖 → 删除重复项；纯代码但较慢 → `slow-baseline`；可拆分 → 按模块拆分；可并行 → 开启 worker；fixture 重建 → 复用只读 fixture。
3. 保留断言；不得为了达标删除无替代的用例。债务写进 `TESTING.md` 的“已知基线债务”表：模块、命令、当前/目标耗时、owner、日期、是否接受、下一步。
4. 未获用户接受时暂停并请求裁决；不得只报告“未获接受”后继续。
5. 迁移慢套件是独立的测试基础设施任务；除非用户要求，当前改动只跑受影响模块并记录债务，不在同一变更里重构整套慢测试。
6. 未达标时明确报告，不得声称全量通过。

## 反模式

- 只测 happy path，错误分支和边界没人覆盖。
- 断言内部调用顺序或私有方法，重构即失败。
- mock 过度，测试实际只验证了 mock 的配置。
- 为 getter/setter、框架行为、无分支代码写测试。
- 在功能基线里启动真实服务、连真实数据库或读用户目录。
- 用随机数据但不固定种子，导致偶发失败。

## 提交前检查

- 改动涉及的每个分支都有对应用例，或有明确不测理由。
- 新增用例在功能基线内，且除受控临时目录外没有真实 I/O、sleep 或共享状态。
- 受影响模块的功能基线全部通过，记录了命令与耗时。
- 没有为了通过而放宽原有断言或删除有效用例。
