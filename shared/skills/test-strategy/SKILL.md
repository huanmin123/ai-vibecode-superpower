# 测试策略

用户显式指定的测试命令或范围覆盖项目默认。授权范围内沿用项目 `AGENTS.md`、`TESTING.md` 或 CI 的命令和门禁。全量测试须由用户单独明确安排，不主动建议或执行。项目或 CI 的全量门禁不等于用户授权本次本地全量测试。
用户口语中的“基准测试”默认指功能基线。

## 决策步骤

1. 确认改动可能影响的可观察行为和风险，查找读取、执行或依赖改动产物的消费者及相应用例。文档、配置和脚本也可能是行为契约。复用已有测试入口，定位和命令方法见[测试选择参考](references/selection-and-commands.md)。已有测试能直接定位时，无需新增映射表、marker 或目录。

2. 定向验证受影响行为、消费者及边界。影响范围不明时查明范围，无法查明则验证已知部分并报告剩余缺口。相关改动形成一个可验收阶段后，集中运行覆盖该范围的快速隔离功能基线。后续只复测结论受影响的部分。

   功能基线应快速、确定、隔离，按风险补充用例和消费者契约测试。它可包含受控的本地集成测试，按模块或套件总耗时管理反馈预算，单例耗时用于定位瓶颈。具体覆盖、依赖和预算方法见[功能基线](references/baseline-tests.md)。

3. 全部任务目标实现后的最终验收确需真实外部依赖或环境验证时，选择对应 flow 的[场景测试](references/scenario-tests.md)。项目已有场景测试时，默认命令须在加载前排除场景模块。

4. 项目有与本次改动相关的 SLO 或性能目标，或 profile、复杂度分析等证据表明改动影响热点时，在本次影响范围内按目标选择[性能测试](references/performance-tests.md)。宽泛关键词本身不足以触发性能测试。

## 运行证据

记录每个命令、退出码、通过、失败和跳过数量、实际耗时，以及与结果有关的环境和未覆盖风险。应有测试的范围若收集到 0 个测试或全部跳过，报告该范围未验证。修 bug 时记录修复前红灯和修复后绿灯。无法复现时写明原因和替代证据。保留原始错误与输出，不把子集结果称为全量结果。

本 skill 不替代 `deep-dive-review` 的独立审查流程。
