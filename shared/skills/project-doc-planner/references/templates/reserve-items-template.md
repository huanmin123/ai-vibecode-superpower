# 储备与触发事项

> 使用说明（复制后删除本段）：复制本文件到目标项目 `docs/储备与触发事项.md`，替换占位符，删除未使用的示例条目。没有条目时保留标题、定位与使用规则。条目转正或放弃后从清单移除，去向与理由随删除提交记录；长期取舍按下方决策记录规则处理，关联草稿随条目迁移或删除。

> 定位：登记当前不做、满足条件后重看或主动决策是否启动的未来事项。本清单不代表排期承诺。

## 使用规则

1. 只登记暂不执行的事项。已明确要做、只是未排期的工作进入 `待办与阻塞事项.md` 的待办分区；必须随代码完成的义务用代码 TODO 表达或直接完成。
2. 新增条目记录背景与价值、可判定的重看触发条件和关键未知。已有调查、方案、验证思路或相关资料可一并记录或链接；没有方案时写明尚待调查的关键问题。决定启动后，再按实际范围补齐可实施的方案与验证方式。
3. 已有技术方案简短时可写在条目内；内容较多时可放入 `reserves/储备方案-<短标题>.md` 草稿，并在条目登记链接。储备阶段允许方案未完成，应区分已知事实与待确认内容。
4. 储备方案草稿存放于 `reserves/`，在本清单条目中链接；已有适用目录索引时同步登记。文档头部标注 `状态：草稿（储备方案，服务 <R 编号>）`。被在用条目引用期间不得按未引用草稿清理；条目转正后将需保留的内容移入待办条目、功能设计或计划并删除原草稿，条目放弃后草稿随同删除。
5. 条目使用稳定编号 `R` + 递增序号（如 `R1`）。条目标题上方保留 `<a id="<小写编号>"></a>` 锚点，跨条目引用写成 `[#R1](#r1)`。编号一经分配不因条目删除复用。引用代码、文档或讨论时提供仓库相对链接或提交哈希。
6. 触发条件满足时重看事项，由维护者决定启动、继续保留或放弃。决定启动后将已有内容及关键未知移入待办清单或对应功能设计/计划，按下方契约边界补充实施方案；决定放弃时移除条目及关联草稿。转正或删除的提交同时包含去向链接或决定理由，需要长期保留的证据进入对应档案。
7. 储备方案不是契约，本清单及其草稿文档不改变当前行为。条目转正涉及稳定契约变化时，先更新项目已有的权威契约；没有适用契约时在项目约定的位置创建，再实施。只有不改变 API、schema、权限、UI、错误语义和稳定质量指标的文档整理、机械性整理或内部重构，才可使用 plan-only。不得把储备方案或计划当作已生效设计。已记录的方案失效条件命中时复核条目，未命中时允许长期休眠，不设强制到期。
8. 启用 `docs/decisions/` 时，转正或放弃时检查是否产生符合记录边界的判断。会长期影响同类取舍的理由先建立决策记录并登记链接；未启用时，把长期理由回写对应设计，或在删除/转正提交说明中保留。普通的优先级、资源或时效原因不建决策。转正形成决策且已记录方案失效条件时，将其纳入决策复核条件。

## 条目格式

记录以下内容；已有方案和关联资料按需添加。

```markdown
<a id="r1"></a>
### R1 <储备标题>

- 背景 / 价值：<值得保留的原因>
- 重看触发条件：<可观察、可判定的条件或需要维护者主动裁决的决策点>
- 关键未知：<启动前需要核实的问题；已无未知时写“无”>
- 已有资料 / 方案：<按需填写已有调查、方案、验证思路、关联代码或文档>
- 方案失效条件：<已有方案时按需填写需要重新评估的条件>
```
