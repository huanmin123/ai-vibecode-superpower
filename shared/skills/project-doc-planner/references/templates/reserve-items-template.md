# 储备与触发事项

> 使用说明（复制后删除本段）：复制本文件到目标项目 `docs/储备与触发事项.md`，替换 `<...>` 占位符，删除未使用的示例条目；没有条目时保留标题、定位与使用规则。条目转正或放弃后立即删除对应条目，去向与理由随删除提交记录，关联的储备方案草稿随条目一并迁移或删除。

> 定位：登记"当前不做、触发条件满足或主动决策后才做"的未来优化与工作储备。每条必须带可执行的技术方案，使未来启动时不必重新调研即可开工。本清单不是排期承诺，不进入当前迭代。

## 使用规则

1. 只登记暂不执行的事项。已明确要做、只是未排期的工作进入 `待办与阻塞事项.md` 的待办分区；必须随代码完成的义务用代码 TODO 表达或直接完成，均不进本清单。
2. 新增条目必须包含：背景与价值、可判定的触发条件、技术方案、验证方式和关联。只有一句描述、没有技术方案的条目不得进入本清单；细节暂时不足时写明"转正前需先产出设计"以及还缺什么，不得留空充数。
3. 技术方案的详略按复杂度抉择：能用几句话写清并让未来执行者直接开工的，直接写在条目内，不建独立文档；设计复杂、几句话说不清的，把完整方案写入 `reserves/储备方案-<短标题>.md` 草稿文档，条目内只保留方案摘要并在"完整方案"行登记相对链接。两种形态都必须写到可独立开工的程度（未来执行者不必重新调研即可开工），不允许条目和文档互相推诿、都不写清。
4. 储备方案草稿存放于 `reserves/` 并在该目录 README 索引登记，文档头部标注 `状态：草稿（储备方案，服务 <R 编号>）`，不进入生效契约，也不混入 `plans/` 执行记录；被在用条目引用期间不得按未引用草稿清理，生命周期完全跟随条目：条目转正后内容升级进待办条目、功能设计或计划并删除原草稿，条目放弃后草稿随同删除，不留孤儿草稿。
5. 条目使用稳定编号 `R` + 递增序号（如 `R1`）。条目标题上方保留 `<a id="<小写编号>"></a>` 锚点，跨条目引用写成 `[#R1](#r1)`。编号一经分配不因条目删除复用。引用代码、文档或讨论时提供仓库相对链接或提交哈希。
6. 条目只有两种出口：触发条件满足后转正（方案细节移入待办清单，或保留在对应功能设计/计划中；实施前按下一条判定 spec 与 plan 的边界），或确认放弃、方案失效后直接删除（关联草稿文档同提交移除）。转正或删除的提交同时包含去向链接或决定理由；需要长期保留的证据随转正载体进入对应档案，本清单不承担档案职责。
7. 储备方案不是契约：本清单及其草稿文档不改变任何当前行为。条目转正涉及稳定契约变化时，必须先创建或更新功能设计（spec）再实施；只有不改变 API、schema、权限、UI、错误语义和稳定质量指标的文档整理、机械性整理或内部重构，才可使用 plan-only。不得把储备方案或计划当作已生效设计。代码或依赖演进命中"方案失效条件"时必须复核条目：更新方案或删除条目；未命中时允许长期休眠，不设强制到期。

## 条目格式

新增条目按以下顺序组织，内容不适用时写"无"：

```markdown
### <编号> <标题>

- 背景 / 价值：<解决什么问题或带来什么收益；现在不做的代价为什么可接受>
- 触发条件：<满足即应启动的条件、外部要求，或需要维护者主动裁决的决策点；写成可观察、可判定的表述，多个条件写明"任一"或"全部"满足>
- 方案失效条件：<模块重构、依赖升级或契约变化到什么程度时本方案必须重新评估；确认长期有效时写"长期有效"并说明依据>
- 规模与风险：<预计改动范围（单点 / 跨模块 / 架构级）、前置依赖和已知风险>
- 验证方式：<转正实施后如何验证，写成可观察结果或测试>
- 关联：<相关代码路径、文档、条目锚点或讨论记录>
- 登记时间：<YYYY-MM-DD>；最近复核：<YYYY-MM-DD 或"未复核">

#### 技术方案

<方案思路：怎么做、为什么这样做。简单条目在此写清全部细节；复杂条目只写摘要，完整方案见下行链接。>

- 改动点：<涉及的模块、文件与预期变化，细到能直接定位改动位置>
- 接口与数据影响：<新增或变化的 API、schema、配置或协议字段；无则写"无">
- 依赖与前置：<需要的库、环境、工具或其他条目；无则写"无">
- 备选取舍：<考虑过并放弃的方向及放弃原因；无则写"无">
- 完整方案：<无（条目内已写清），或 reserves/储备方案-<短标题>.md 相对链接>
```
