# 报告与覆盖台账

报告的读者要能据此复核每条结论、判断风险顺序、知道哪些地方没查。不要把报告写成漏洞百科，也不要用数量制造安全感。

## 1 报告结构

```markdown
# 安全审计报告：<项目/模块>

## 元信息
- 目标：<路径/仓库> @ <commit/ref>
- 模式：full | triage | exhaustive | diff | class:<名称>
- 范围：<包含的模块/入口>
- 非范围：<明确排除的内容>
- 时间：<开始/结束>
- 部署假设：<公网/内网/未知，以及依据>
- 工具：<名称/版本/规则或数据库版本>

## 结论摘要（≤10 行）
- 确认发现：P0 x 条，P1 x 条，P2 x 条，P3 x 条
- 最需要先处理的三项及原因
- 待运行时验证：x 条
- 未覆盖：x 项（列关键项）
- 声明：本报告只证明已覆盖范围内的结论，不证明项目不存在其他漏洞

## 攻击路径
```

## 2 Finding 模板

````markdown
### SEC-001 <一句话：谁在什么条件下能做什么>

- 状态：confirmed | needs-runtime
- 类别：CWE-639（Authorization Bypass Through User-Controlled Key）
- ASVS：V8 Authorization（按 ASVS 5.0.0 章节核对）
- 层 / 证据等级：L1 / E1
- 攻击画像：<匿名 | 普通用户 | 跨租户 | 低权管理员 | 内部人 | 服务账号>
- 外部核实：<公告 ID + 检索日期；不涉及则写明>
- 优先级：P1
- 严重度：high
- Confidence：high
- 位置：`db.js:14`（sink）
- 来源：`GET /api/notes/:id` 的路径参数 `id`（登录用户可控）
- 暴露假设：该路由由公网网关暴露；若仅内网可达，优先级降为 P2

**证据链**

```text
source  routes/notes.js:21   const id = req.params.id
hop     routes/notes.js:22   const note = await findNote(id)
sink    db.js:14             db.query('SELECT * FROM notes WHERE id = ?', [id])
缺失    routes/notes.js:20   仅 requireAuth，无 owner_id 谓词
```

**为什么现有控制无效**

`requireAuth` 只验证登录，不验证对象归属；查询未包含 `owner_id` 条件；响应返回完整对象。

**影响**

任意登录用户可读取他人笔记，包含标题、正文与附件路径；ID 为自增整数，可枚举。

**证伪记录**

| 检查 | 结果 |
| --- | --- |
| 可达性 | 路由已注册，未被 flag 关闭 |
| 攻击者控制 | `id` 直接来自路径参数，无格式限制 |
| 控制有效性 | 查询使用绑定参数，但无对象级授权 |
| 版本现实 | 按锁文件版本核实，无全局 scope 拦截 |
| 影响 | 返回完整对象，含敏感字段 |

**修复建议**

在查询中加入当前登录用户的归属谓词：`WHERE id = ? AND owner_id = ?`。

**复核方式**

用两个测试账号 A/B，B 请求 A 的对象 ID，确认返回 404 且不泄露对象存在性。
````

## 3 攻击路径

P0/P1 必须有完整攻击路径：画像、已有能力、目标、入口、缺失控制、前置条件、影响、检测缺口。多条 finding 共享同一路径时合并路径并引用各 finding；不同根因或修复点保留独立 finding。同根因且修复点相同的变体可合并，影响范围写全。

例如，路径表中一条链可在关联发现列同时引用 `SEC-001`、`SEC-002`；正文分别记录两个 finding 的根因、证据和修复点。

路径只写到"能达成目标"为止，不写可直接武器化的完整载荷；但要保留复核所需的入口、条件与证据位置。路径中的每一跳引用 finding ID 或适用层的证据定位；代码路径逐跳引用 `file:line`。

## 4 状态与优先级

| 状态 | 定义 | 进入摘要 |
| --- | --- | --- |
| `confirmed` | 适用层的证据链完整，控制确实缺失或可绕过 | 是 |
| `needs-runtime` | 路径成立，但依赖尚未核实的运行时条件 | 单列 |
| `lead` | 缺关键环节，只作为后续入口 | 否 |
| `clean` | 已排查且确认不成立 | 否，进"已查清白" |

优先级见 [review-loop.md](review-loop.md) 第 6 节。报告中的排序以优先级为准；严重度只作为补充标签。P0/P1 必须给出"为什么现在就要处理"的一句话，不写套话。

## 5 覆盖台账

台账是"查过什么"的正面证据，不是形式。按实际视角记录并追溯到 lenses；新增视角或层须明确列出。`exhaustive` 的每格保留可回溯 ID 及入口、信任边界、视角、层、画像、数据资产、状态转换和新增轴值，可用分片或汇总展示，但必须能还原完整组合与各格状态、证据和理由。

规则：

- 每个格子只能是 `confirmed` / `needs-runtime` / `lead` / `clean` / `n/a` / `not-covered`，不能留空。
- `clean` 必须附排查证据与判定理由；`n/a` 必须有证据证明该组合不适用并说明理由。
- 台账粒度到入口或模块，不写到"整个项目已检查"。
- 未检查或无法完成的格标为 `not-covered`，写明原因（缺代码、缺依赖、缺环境、缺授权、超出范围或触及上限）和已知证据，不得写成 `n/a` 或 `clean`；同时在未覆盖节汇总。触及上限时报告未完成穷举。

## 6 外部核实记录

| Finding | 问题 | 来源 | 来源类型 | 检索日期 | 适用性结论 | 未验证项 |
| --- | --- | --- | --- | --- | --- | --- |

规则：

- 只记录真正支撑结论的来源；不为凑数堆链接。
- 来源类型按 [external-research.md](external-research.md) 的可信度分级：vendor/osv/ghsa/nvd/distro/research。
- 适用性写清 affected range、代码可达性、配置前置、backport 状态。
- 无法确认的写 `unverified`，并说明"还需要什么"。

## 7 供应链与配置的写法

单独一节，每条包含：组件/配置、锁定版本、影响条件、可达性、可利用前提、修复版本/缓解、未验证部分。

不要把"依赖有 CVE"直接写成与代码漏洞同级的 finding；也不要把"缺失安全响应头"混进漏洞统计。加固建议统一放最后一节，标注为建议而非漏洞。

## 8 写作规则

- 结论先行：标题写清"谁在什么条件下能做什么"，不写"存在 SQL 注入风险"这种无主语表述。
- 事实与判断分开：代码事实、版本事实、部署假设、推断分别标注。
- 代码证据逐跳给 `file:line`；引用的代码要与当前 ref 一致，行号偏移时以代码片段为准。非代码证据给授权资源标识或只读命令、执行身份、采集时间及相关输出定位；配置/部署已观察事实与假设、未验证条件分别标注。
- 不写"可能""也许"作为结论；不确定就降级为 lead 或 needs-runtime。
- 影响要具体：哪个资产、哪类数据、多大范围、攻击者获得什么；不写"可能造成严重后果"。
- 修复建议落在具体位置与做法；引用权威指南时给章节/URL，不堆链接。
- 不泄露利用细节到不必要的程度；报告中可以省略可直接武器化的完整载荷，但必须保留复核所需的路径与条件。
- 不在报告中复述工具原始输出；保留工具名、规则 ID 与证据位置即可。

## 9 SARIF 输出（可选）

需要与代码扫描平台集成时，把 confirmed 发现映射为 SARIF：

- `ruleId`：CWE 编号或自定义规则 ID；
- `level`：映射优先级（P0/P1 → error，P2 → warning，P3 → note）；
- `locations[].physicalLocation`：sink 的 URI 与行列（1-based）；
- `message.text`：标题 + 影响；
- `partialFingerprints`：用文件路径 + sink 特征生成稳定指纹；
- `suppressions`：不放 confirmed 项；已接受风险单独记录并写明理由。

SARIF 只是交换格式，不改变结论；不要为了平台展示把 lead 提升为 finding。

## 10 报告自检

交付前逐项确认：

- [ ] 每条 confirmed 都有完整证据链、控制失效原因、影响与复核方式。
- [ ] P0/P1 都有攻击路径，写清画像、已有能力、目标、前置条件与检测缺口。
- [ ] 每条 finding 标注了所属层与证据等级，没有把 E1/E2 推断写成 E3 事实。
- [ ] 外部事实（CVE/公告/默认行为/修复版本）有来源、版本与检索日期，且来源确实打开过。
- [ ] 每条 confirmed 都经过了未参与取证的证伪，或记录了单人证伪过程。
- [ ] 所有 `file:line` 与当前 ref 一致，代码片段可复核。
- [ ] 框架/库默认行为有版本依据，不是凭记忆。
- [ ] 供应链与配置问题没有被写成代码漏洞。
- [ ] 台账每格有状态与理由；`exhaustive` 的完整轴值和格 ID 可回溯，未覆盖项与触顶状态已列明。
- [ ] 层覆盖台账覆盖了声明的每个层；未访问的层标为 not-covered，没有推断。
- [ ] 摘要中的数字与正文一致。
- [ ] 保留了"覆盖不等于安全"的声明。
