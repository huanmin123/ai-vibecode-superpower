# 任意技术栈的适配方法

本文件不提供"全语言漏洞清单"。目标栈可能很新、很小众，或版本与常见资料不同。可靠的做法是至少找到三类东西，再按目标版本核对行为。

## 1 至少三类位置

任何栈的安全审计都**至少**从这三类位置入手：

| 类别 | 要找什么 | 找不到时的后果 |
| --- | --- | --- |
| 入口注册点 | 路由、订阅、任务、CLI、Webhook、Server Action 在哪里注册到运行时 | 漏掉未在 UI 出现的接口 |
| 控制点 | 认证、授权、校验、编码、限流、审计在哪一层统一执行 | 把"框架默认"误当成"已防护" |
| 逃逸口 | 框架提供的 raw/unsafe/bypass/disable 接口，以及语言级的动态执行能力 | 只审正常路径，漏掉真正危险的入口 |
| 目标独有机制 | 插件、规则引擎、工作流、导入导出、模型/Agent 工具调用 | 漏掉非标准入口与数据流 |

以上类别是下界，不是全集；目标有表外机制时新增一类，并在台账中说明它如何进入系统、经过哪些控制。

审计不是把框架 API 背一遍，而是确认：**每个入口都经过控制点；每个逃逸口都有与语义匹配的约束。**

## 2 入口注册点

按栈找启动与装配位置，而不是按目录猜：

- 读入口文件（`main`、`app`、`server`、`Program`、`index`、`cmd/`），看路由/中间件如何挂载。
- 找路由注册的语法特征：装饰器、注解、路由表、`Router` 对象、文件系统路由、schema 定义。
- 找"运行时生成"的入口：反射、插件、动态导入、配置驱动的 handler、Server Action。
- 找非 HTTP 入口：消息订阅、定时任务、队列消费者、CLI、文件监听、Webhook。
- 若框架提供路由列举命令或调试端点，优先使用；没有就静态追注册链。

## 3 控制点

沿入口向下，确认控制发生在哪一层：

- 全局：中间件、过滤器、拦截器、guard、网关、数据库策略。
- 分组：路由组、蓝图、namespace、controller 级注解。
- 单点：handler 内的显式检查、策略对象、资源级授权。
- 数据层：查询谓词、行级安全、唯一约束、字段级权限。

记录控制的**注册顺序与作用范围**。集中式控制最常见的缺陷不是"没写"，而是"没覆盖到某个入口"或"被更晚注册的路由绕过"。

## 4 逃逸口

每个框架都有"绕过安全默认"的接口。用语义搜索找它们，再逐个确认约束。下表是搜索语义示例，不是 API 清单；具体符号以目标代码和版本文档为准：

| 语义 | 搜索线索 |
| --- | --- |
| 原始查询 | `raw`、`unsafe`、`unprepared`、`execute`、`query` + 字符串拼接、`text(` |
| 动态执行 | `eval`、`exec`、`Function`、`compile`、`invoke`、`send`、`constantize`、`dynamic import` |
| 反序列化 | `deserialize`、`unmarshal`、`pickle`、`unserialize`、`readObject`、`fromXML`、`loads` |
| 文件/路径 | `join`、`resolve`、`open`、`readFile`、`sendFile`、`extract`、`archive` |
| 外部请求 | `fetch`、`http.Get`、`requests`、`RestTemplate`、`curl`、`openConnection` |
| 模板/渲染 | `render`、`template`、`innerHTML`、`Html.Raw`、`safe`、`|raw`、`{!!` |
| 关闭安全 | `verify=False`、`InsecureSkipVerify`、`danger_accept`、`disable`、`permitAll`、`AllowAny`、`csrf_exempt` |
| 批量绑定 | `bind`、`fill`、`assign`、`permit!`、`@ModelAttribute`、`mass assignment` |

找到逃逸口后问三件事：输入是否受攻击者控制？约束是否覆盖该语义？约束是否在逃逸口之前执行？

## 5 按栈定位：找位置，不背表

不要维护"某语言的路由/鉴权/逃逸口 API 表"：框架版本、封装层、项目自建抽象都会让它失效。按顺序在目标里找：

1. 启动文件 → 路由、中间件、订阅、任务注册。
2. 路由注册语法 → 入口全集（含未在 UI 出现的）。
3. 控制装配 → 认证、授权、校验、限流在哪一层，注册顺序与作用范围。
4. 第 4 节的语义搜索 → 逃逸口。
5. 包元数据 → 对应版本文档/源码 → 确认默认行为。

同一概念在不同栈里名字不同（middleware/guard/filter/decorator/policy），但位置和作用稳定；不要依赖"我列过这个框架"来保证覆盖。

## 6 遇到未知栈

1. 从包元数据/registry 找到官方安全指南与"security considerations"章节；先切到目标版本，没有版本切换时以安装源码为准。
2. 找到路由表或路由列举方式；列出所有入口，包括非 HTTP。
3. 读启动装配，确认中间件顺序与作用范围。
4. 用第 4 节的语义线索找逃逸口；再读依赖源码确认行为。
5. 查当前漏洞公告与生命周期状态（OSV/GHSA/厂商公告/EOL），不要依赖记忆。
6. 记录：来源 URL、版本、核实日期、未验证项。

## 7 时效性

安全事实会过期：默认值会变、API 会废弃、漏洞会新披露、版本会 EOL。因此：

- 本 skill 中的任何示例都只是**起点**，不是当前事实。
- 版本相关判断必须在审计时核对：锁文件版本 + 对应版本文档/源码。
- 漏洞判断以审计当日的公告数据库为准；报告写明查询时间与数据源。
- 无法核实的行为写"未验证"，不写"默认安全"或"默认危险"。
- 发现资料与代码冲突时，以目标版本的实际行为为准，并记录冲突。

## 8 反模式

| 反模式 | 后果 |
| --- | --- |
| 凭记忆列某框架的危险 API | 漏掉新 API、误判已废弃行为 |
| 把本文示例当完整清单 | 覆盖率假象 |
| 只读业务目录，不读启动装配 | 漏掉中间件顺序与未挂载代码 |
| 把框架"有安全功能"当成"已启用" | 默认值与配置未核实 |
| 用最新版本文档判断旧版本 | 结论与运行版本不符 |
| 遇到不认识的栈就跳过 | 未覆盖项被隐藏 |
