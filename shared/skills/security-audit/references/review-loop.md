# 排查、取证与证伪

本文件是审计的执行细则。核心顺序：**先盘 sink，再追 source，最后证明控制无效**。反过来做（先读业务再猜漏洞）会漏掉大量边缘入口，也容易把无害代码写成漏洞。

代码路径逐跳记录当前 ref 的 `file:line`。非代码审查以授权范围内的资源标识或只读命令、执行身份、采集时间和相关输出定位构建可复核证据链；分别记录配置/部署的观察事实与未验证条件，不把仓库推断写成运行事实。

## 1 排查单元

一个排查单元 = 一个 sink 类别 × 一个入口域。不要按文件分配，也不要只按漏洞名分配。

对每个 sink：

1. 记录 sink 位置、调用方式、进入该 sink 的参数名。
2. 反向找参数来源：请求参数、请求体、头、cookie、上传文件、数据库字段、队列消息、第三方响应、文件名、环境变量。
3. 记录中间每一跳的函数与控制。
4. 判断控制是否覆盖该 sink 的语义（见第 3 节）。
5. 产出候选：`sink → source 假设 → 缺失/失效的控制 → 预期影响`。

数据库字段也算不可信来源：存储型 XSS、二次注入、Stored SSRF 都从"已入库的数据"进入 sink。只把 HTTP 输入当 source 会漏掉一整类问题。

## 2 两种追踪方向

**反向追踪（sink → source）**：用于注入、路径、SSRF、反序列化、文件类。从一个具体危险调用出发，逐跳向前找调用者，直到请求边界或证明不可达。每一跳记录：

```text
sink:   routes/files.js:42  fs.readFile(path.join(UPLOAD_DIR, req.query.name))
hop 1:  routes/files.js:38  const { name } = req.query
source: HTTP GET /api/files query.name
controls: 无路径规范化、无 basename、无扩展名白名单
```

**正向追踪（entry → sink）**：用于授权、业务逻辑、状态机、竞态。从一个入口出发，沿主要分支检查每个敏感操作前是否有授权与状态校验。授权类问题通常不是"某个 sink 危险"，而是"某条路径少了一个判断"。

两种方向都要用：只做反向会漏授权，只做正向会漏深层注入。

## 3 控制类型与有效性

判定控制时先归类，再判断它是否覆盖当前 sink 的语义。下表是控制分类，不是完整控制清单；按目标栈补充，重点看控制是否覆盖当前 sink 语义。

| 控制 | 有效条件 | 常见失效 |
| --- | --- | --- |
| 类型/格式校验 | 在进入 sink 前执行，且约束覆盖危险字符或结构 | 只校验长度；只校验前端；正则未锚定；校验后又拼接 |
| 白名单 | 完整枚举允许值，默认拒绝 | 只做前缀/后缀匹配；大小写与编码未归一；可被 `..`、绝对路径、URL 解析差异绕过 |
| 参数化/预编译 | 值只作为绑定参数，SQL/查询结构不含用户输入 | 拼接表名/列名/排序方向；ORM 的 raw/extra 接口；`LIKE` 拼接；多语句 |
| 输出编码 | 编码上下文与输出位置一致（HTML/属性/JS/URL/CSS） | 在错误上下文编码；先解码后拼接；`innerHTML` 配合 HTML 编码；富文本未净化 |
| 对象级授权 | 先取对象，再用当前主体校验归属/租户，且校验不可跳过 | 只校验登录；列表接口做了过滤、详情接口没做；校验在异常分支被绕过 |
| 租户谓词 | 租户来自服务端身份，查询、缓存、存储、任务都带租户 | 租户来自请求体/头；缓存 key 不含租户；后台任务只带对象 ID |
| 加密/签名 | 算法与用途匹配，密钥受管，验证不可关闭 | 用哈希代替口令哈希；固定 IV/nonce；`verify=False`；JWT 未限定算法 |
| 沙箱/隔离 | 隔离边界由运行时强制，且不可从被隔离代码逃逸 | 模板沙箱可被对象属性链绕过；`vm` 被当作安全边界；子进程仍共享文件系统 |
| 配置/部署 | 生产配置实际生效且不能被请求影响 | 只改仓库默认；环境变量可被覆盖；debug/管理端口对外 |

判定结论只有三种：**控制缺失**、**控制存在但被绕过**、**控制有效**。第三种写入"已查清白"，前两种进入证伪。

## 4 证伪清单

对每条候选逐项执行，记录结果；不能执行的项写明原因并降低 confidence。

| 检查 | 要证明什么 | 具体做法 |
| --- | --- | --- |
| R1 可达性 | 代码真的会被执行 | 路由是否注册、函数是否被调用、是否死代码、是否被 feature flag/环境判断关闭、是否只在测试/脚本中使用 |
| R2 攻击者控制 | 值真的能由攻击者决定 | 追到请求边界；检查 schema/类型/长度/枚举约束；检查是否经过签名、加密、服务端映射 |
| R3 控制存在 | 上游是否已有防护 | 中间件、全局 guard、框架默认转义、参数绑定、数据库约束、网关规则、序列化白名单 |
| R4 控制有效 | 防护是否覆盖当前语义 | 编码上下文是否匹配、校验是否在 sink 前、白名单是否可绕过、授权是否作用于该对象而非仅该路由 |
| R5 版本现实 | 当前版本/平台行为是否如假设 | 从锁文件确认版本；必要时读依赖源码或官方文档；平台相关行为（路径、归档、TLS）按目标平台核对；不凭记忆断言默认值 |
| R6 影响成立 | 攻击者实际得到什么 | 具体资产、权限提升、数据范围、可否持久化、是否可横向移动；不能只说"可能泄露" |
| R7 前提合理 | 利用条件是否现实 | 所需角色、用户交互、竞态窗口、配置项、网络位置；条件不现实就降级 |
| R8 去重 | 是否与其他条目同根因且修复点相同 | 同根因同修复点的变体合并并写全影响范围；不同根因或修复点分别保留 finding，即使共享攻击路径 |

证伪的目标是**推翻**，不是确认。找不到反证才保留；找到任一反证就降级或撤销，并把反证写进 `refutation`。

## 5 状态判定

| 状态 | 条件 | 是否计入发现 |
| --- | --- | --- |
| `confirmed` | 适用层的证据链完整，控制确实缺失或可绕过，影响有证据支持 | 是 |
| `needs-runtime` | 已知路径成立，但结论依赖尚未核实的部署/运行时条件 | 单列，不计入 confirmed |
| `lead` | 缺少 source、可达性或控制判定的关键环节 | 否，作为后续入口 |
| `clean` | 已排查且确认控制有效或不可达 | 否，写入台账 |

`confirmed` 不等于"一定能在生产利用"；它只表示证据支持的适用层面成立。暴露假设仍要写在 finding 里。

版本相关结论的默认状态：

- 只有清单、没有锁文件或安装产物时，版本相关行为默认 `needs-runtime`；传递依赖与部署安装树都未验证。
- 直接依赖在清单中精确固定（非 `^`/`~`/范围）且无 override 机制时，可核对该声明版本的源码/文档，并在其他利用前提有完整证据时确认该声明依赖在这些前提下可利用；须说明无锁文件、传递依赖与部署实际版本未验证，不把声明版本当作运行事实。
- 运行时/平台相关行为（归档解压、路径规范化、TLS、序列化）不能只凭 API 名判定；目标平台或版本未知时写 `needs-runtime`。

## 6 定级

优先级按**实际可利用性 × 影响**，不按类别标签：

| 优先级 | 判据 | 典型 |
| --- | --- | --- |
| P0 | 未认证或普通用户可远程直接利用；RCE、认证绕过、全量或跨租户数据泄露 | 未授权命令注入、JWT 算法绕过、公开的管理接口 |
| P1 | 需登录或特定条件；越权访问、敏感数据泄露、数据篡改、内网可达 | IDOR、存储型 XSS 打管理员、SSRF 触达元数据服务 |
| P2 | 利用条件受限或影响有限；需要交互、特定配置、低权限数据 | 仅影响本人的 XSS、受限路径穿越、低危信息泄露 |
| P3 | 加固项、纵深防御缺失、信息暴露 | 缺失安全响应头、详细错误页、非敏感配置 |

CVSS 作为补充，不给单一数字了事：

- 按 [CVSS v4.0 规范](https://www.first.org/cvss/v4.0/specification-document)给分并列出完整 vector 和依据：Base 必填 AV/AC/AT/PR/UI/VC/VI/VA/SC/SI/SA；有适用环境证据时附加 Environmental 指标并标为 **CVSS-BE**。
- 缺少环境证据时给 Base 分，标注 "CVSS-B，未调整"，并说明它不代表实际风险。
- 严重度与优先级冲突时，以优先级解释实际处置顺序，并说明原因。

## 7 常见误报模式

| 模式 | 为什么不是 finding | 正确处理 |
| --- | --- | --- |
| 只匹配到危险 API | 没有攻击者控制或不可达 | 记为 lead，补 source 与可达性 |
| 死代码/未接线 handler | 不会被触发 | 记为 clean（死代码），除非有动态加载/反射调用证据 |
| 框架默认已防护 | 例如模板自动转义、ORM 参数化 | 核实版本与配置后记 clean |
| 测试、示例、fixture 中的代码 | 默认不在生产路径，但如果用户明确把该目录作为审计目标，应按"这些代码被部署时"的行为评估，并注明语境 | 默认记 clean；被指定为目标时按正常 finding 处理 |
| 依赖 CVE | 组件存在漏洞不等于代码路径可利用 | 进供应链章节，按可达性/版本/暴露分诊 |
| 缺失安全响应头 | 纵深防御建议，不是漏洞 | 放加固建议 |
| 仅前端校验缺失 | 服务端仍有校验 | 记 clean；若服务端也没有才是 finding |
| 自身可控的 XSS | 只能攻击自己，不构成跨用户影响 | 降为 P3 或加固项 |
| WAF/网关作为唯一防护 | 可被编码、协议差异、白名单路径绕过 | 不作为有效控制，只能作为纵深防御 |
| 硬编码测试密钥 | 非真实凭据且无权限 | 记 clean；真实凭据按密钥流程处理 |

误报模式也是下界。出现表外形态时按证据判定，不硬套现有条目；如果某种形态反复出现，补进本表。

## 8 并行拆分

| 实例 | 输入 | 输出 | 禁止 |
| --- | --- | --- | --- |
| A 授权 | surface map 的入口与授权矩阵 | 每条入口的授权判定与候选 | 顺带做注入定性 |
| B 注入/解释器 | 入口清单 + sink 表 | sink→source 路径与候选 | 直接给最终严重度 |
| C 数据/文件/网络 | 上传、下载、反序列化、外部请求入口 | 路径与候选 | 扩大到无关模块 |
| D 身份/会话/加密 | 认证、会话、token、密钥位置 | 控制判定与候选 | 凭记忆断言库默认值 |
| E 供应链/配置 | 清单、锁文件、CI、容器、配置 | 依赖与配置问题 | 把 CVE 直接写成代码漏洞 |
| 证伪实例 | 单条候选 + 相关代码片段 | 推翻或保留 + 理由 | 参与该条取证 |

域是下界；目标有表外域（插件、规则引擎、模型/Agent 工具调用、数据管道）时新增分片，不要硬塞进现有五域。

验证实例只输出输入候选的结论；输出 ID 集合应与输入一致，不得遗漏或新增 finding。新发现写入 `new_leads`，回到生成/合并，不混入本轮 finding。

无法并行时按 A→B→C→D→E 顺序执行。每个域结束先落盘候选，再进入下一域，避免上下文互相污染。证伪步骤对每条 confirmed 单独执行，不能合并成"整体再看一遍"。

## 9 记录与停止

- 每个域结束更新覆盖台账：入口 × 类别 = 状态 + 证据位置 + 理由。
- 出现新 lead 时回到对应域补查，不在报告阶段临时补证据。
- 连续一轮排查没有新增 lead，且所有 confirmed 完成证伪，才进入报告。
- 因缺少代码、依赖、环境或授权而无法完成的格标为 `not-covered` 并写入"未覆盖"，不写成 `clean` 或 `n/a`。
