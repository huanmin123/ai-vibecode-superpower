# 授权、越权与租户隔离

授权类问题是实际审计中产出最高、扫描器覆盖最差的一类。它们通常不是"危险的 API 调用"，而是"某条路径少了一个判断"，因此必须按入口逐条核查，不能靠 sink 扫描。

## 1 授权模型

每个受保护操作都要回答四个问题：

| 要素 | 问题 | 不可信来源 |
| --- | --- | --- |
| 主体 Subject | 是谁？身份从哪里来？ | 请求体里的 `userId`、可伪造的头、未验签的 token 声明 |
| 动作 Action | 允许做什么？读、写、删、导出、审批、 impersonate | 前端传入的 `action`、隐藏字段 |
| 对象 Object | 作用于哪个资源？归属谁？ | 路径/查询里的对象 ID |
| 上下文 Context | 哪个租户、哪个组织、什么状态、什么时间窗 | 请求体/头里的 `tenantId`、`orgId`、`role` |

授权的正确形式是：**服务端身份 + 对象归属/租户谓词 + 动作许可**，三者同时成立。缺任一维度都可能构成越权。

## 2 逐入口核查

以 surface map 的入口表为清单，对每条入口记录：

```text
入口:      GET /api/notes/:id
认证:      requireAuth（JWT）
功能级:    无（任何登录用户可访问）        ← 是否合理？
对象级:    无；查询为 WHERE id = ?         ← 缺失，候选
租户:      无
判定位置:  routes/notes.js:21
```

### 2.1 功能级授权

- 路由是否在受保护的组/前缀/中间件之后注册？注册顺序是否让后面的中间件覆盖不到它？
- 全局 guard/过滤器是否被路由级配置、`@Public`/`@AllowAnonymous`、排除列表绕过？
- 管理接口是否只在前端隐藏菜单，服务端仍可被普通用户直接调用？
- 导出、批量、调试、内部 API 是否单独注册而漏掉防护？
- 方法级注解是否真的启用（例如方法安全未开启时注解不生效）？

### 2.2 对象级授权

按 ID 取对象后，必须验证当前主体对该对象有权限。常见缺陷：

- 只校验登录，不校验归属（IDOR/BOLA）；
- 列表接口做了 `WHERE owner_id = ?`，详情/更新/删除接口没做；
- 校验用了请求体里的 `ownerId` 而不是数据库中的归属；
- 先返回数据，再在序列化层"过滤"，但敏感字段已进入响应；
- 批量接口只校验第一个对象，其余对象未校验；
- GraphQL 只校验边/节点类型，未校验 `node(id:)` 指向的对象；
- 文件下载只校验登录，未校验文件归属或租户。

**核实方法**：从路由追到实际查询，确认查询谓词是否包含主体或租户条件；确认该校验不在可跳过的分支里；确认对象不存在与无权限返回一致（避免枚举）。

### 2.3 租户隔离

多租户系统要把隔离检查扩展到所有携带租户数据的路径：

| 路径 | 检查 |
| --- | --- |
| 数据库查询 | 每条查询是否带租户谓词；是否依赖调用方传入的租户 ID |
| 缓存 | key 是否含租户；是否跨租户复用同一 key |
| 对象存储 | 路径/桶是否按租户隔离；签名 URL 的范围 |
| 队列/任务 | 消息是否只带对象 ID 而不带租户；消费者是否重新校验 |
| 搜索索引 | 文档是否带租户过滤；是否使用全局索引 |
| 日志/导出 | 是否可能把 A 租户数据写入 B 租户可见位置 |
| 数据库 RLS | 是否启用且未被 `BYPASSRLS` 或超级用户绕过 |

租户 ID 必须来自服务端身份或服务端映射，不能直接信任请求体/请求头。

### 2.4 管理面与服务间

- 管理接口是否独立部署/独立鉴权，还是与用户接口共用同一套低权 token？
- 服务间调用是否使用可被外部复用的静态密钥/共享 token？
- 内部 API 是否错误地暴露在公网入口（同一 router、同一网关路由）。
- impersonate/代操作功能是否记录审计、是否限制目标与时效。

## 3 身份来源可信性

| 来源 | 可信条件 |
| --- | --- |
| Session cookie | 服务端可验证签名、绑定会话、不可伪造 |
| Bearer JWT | 验签、限定算法、校验 `iss`/`aud`/`exp`、不信任 `role` 以外的自定义声明除非签发方可信 |
| API key | 服务端映射到主体与权限；不可由请求体覆盖 |
| 网关注入头（`X-User-Id` 等） | 应用只能从受信网关注入，且外部请求无法直接设置同名头 |
| 请求体/查询参数中的 `userId`/`tenantId`/`role` | 一律不可信，除非与已验证身份交叉校验 |

JWT 的 `role`/`tenant` 声明可以作为授权依据，前提是签名验证正确且签发方受信；但仍要检查对象归属，不能因为 token 里有租户就跳过查询谓词。

## 4 批量赋值与授权

批量赋值本身是数据完整性问题，但它经常直接导致提权：

- 用户资料更新允许绑定 `role`/`isAdmin`/`permissions`；
- 注册接口允许绑定 `tenantId`/`orgId` 进入其他租户；
- 邀请/成员接口允许绑定 `ownerId`；
- 配置合并允许覆盖 `auth`/`security` 字段。

核实：敏感字段是否在绑定白名单中；绑定后再做授权检查不能弥补"字段已被写入"。

## 5 前端伪授权

以下都不构成服务端授权，只能作为 UX：

- 菜单/按钮隐藏、路由守卫、组件条件渲染；
- 前端传入的 `role`/`permissions` 被后端直接采用；
- 只在客户端校验对象归属；
- 隐藏字段传递 `isAdmin`。

发现前端隐藏但服务端无校验时，按服务端实际可达性判定，不因"UI 上看不到"降级。

## 6 核实步骤

1. **列全入口**：从路由注册、GraphQL schema、消息订阅、任务注册、Server Action 导出逐一枚举，不遗漏未在 UI 出现的接口。
2. **画调用链**：入口 → 中间件/guard → handler → 查询/操作。记录每一跳的 file:line。
3. **找判定点**：功能级判定、对象级判定、租户谓词分别在哪里；没有就记为缺失。
4. **验证判定覆盖**：判定是否作用于当前对象；是否在异常/提前返回/批量分支被跳过；是否只对部分 HTTP 方法生效。
5. **构造双主体场景**（静态推演）：普通用户 A 持有对象 X，用户 B 用自己的凭证请求 X 的 ID，代码是否返回 X。不能只看"有没有 `requireAuth`"。
6. **检查一致性**：列表、详情、更新、删除、导出是否采用同一套判定；新增接口是否复用了旧接口的判定。
7. **记录假设**：角色模型、租户来源、网关行为无法从代码核实时，写入 `needs-runtime` 或降低 confidence。

## 7 误报陷阱

| 现象 | 可能不是漏洞 |
| --- | --- |
| 路由没有显式授权 | 全局中间件/父路由组/网关已统一强制，且注册顺序正确 |
| handler 用 `findById` | 之后调用了策略对象/`check_object_permissions`/数据库 RLS |
| 列表没有过滤 | 查询层/序列化层/数据库视图已按租户限制，需追到实际 SQL |
| 前端显示所有数据 | 接口返回的是脱敏 DTO，敏感字段未出库 |
| 管理接口无注解 | 整个路由前缀在安全配置中被 `hasRole` 保护 |
| 返回 404 而非 403 | 可能是刻意的防枚举设计，不是缺陷 |

每条"看起来缺失"的授权都要追到最终查询或策略执行点；只看到 handler 没有 `if` 就下结论，是最常见的误报来源。

## 8 输出要求

授权类 finding 必须写清：

- 攻击者需要的身份（匿名/普通用户/某租户用户/服务账号）；
- 目标对象的获取方式（ID 是否可枚举、是否可从列表/导出/日志获得）；
- 缺失的判定维度（功能级/对象级/租户/动作）；
- 影响范围（单个对象、同租户全部、跨租户、管理面）；
- 修复建议要落在具体判定点，而不是泛泛写"增加权限校验"。
