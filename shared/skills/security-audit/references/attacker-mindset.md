# 攻击者视角

审计不是"找漏洞"，而是回答：

> 谁，已经拥有什么，想得到什么，最便宜的路径是什么，还差哪一步？

漏洞只是路径上的一个节点。同一个缺陷，对不同攻击者的价值可能完全不同；一条低危信息泄露，可能是另一条高危路径的起点。

## 1 攻击者画像

先列画像，再谈漏洞。每个画像都要写清"已经能合法做什么"，越权与提权的本质是**超出这个合法集合**。画像是推导工具，不是穷举；按目标业务增删，重点是每个画像的权限边界。表外画像（供应商、合作伙伴、匿名 API 调用方、设备身份、外部运营）出现时必须新增，不要套用最接近的旧画像。

| 画像 | 已有能力 | 典型目标 | 约束 |
| --- | --- | --- | --- |
| 匿名外部 | 访问公开入口、枚举、爬取 | 信息泄露、认证绕过、公开管理面 | 无凭证、可能被限流/WAF |
| 普通注册用户 | 自己的账号与数据、正常业务操作 | 读他人数据、提权、免费获取付费能力 | 需登录、可能有频率限制 |
| 同租户低权用户 | 同租户内部分数据 | 租户内越权、角色提升 | 租户边界内 |
| 跨租户用户 | 另一租户的合法账号 | 跨租户读写、租户枚举 | 需另一个租户账号 |
| 低权管理员/运营 | 部分后台能力 | 超级管理员、导出全量、改配置 | 后台入口、审计 |
| 内部人/离职者 | 内网、代码、部分凭据 | 持久化、数据带走、绕过审计 | 可能已有合法权限 |
| 服务账号/机器身份 | API、队列、CI、云角色 | 横向移动、读取密钥、篡改产物 | 权限范围、网络策略 |
| 供应链参与者 | 依赖、构建、发布链路 | 投毒、后门、窃取签名 | 需进入依赖或构建链 |

如果一条"漏洞"让某个画像做到了它本来就能做的事，那不是漏洞。

## 2 资产与目标

从 surface map 的数据分级出发，把"攻击者想要什么"具体化：

| 目标 | 具体资产 | 攻击者收益 |
| --- | --- | --- |
| 机密性 | 凭据、密钥、PII、租户数据、源码、内部文档 | 直接变现、横向移动、勒索 |
| 完整性 | 余额、订单、库存、角色、配置、审计日志 | 欺诈、掩盖痕迹、持久化 |
| 可用性 | 服务、配额、成本、队列 | 勒索、竞争破坏、成本攻击 |
| 身份与权限 | 会话、token、角色、服务账号 | 冒充、提权、长期驻留 |
| 信任与合规 | 供应链、客户信任、审计结论 | 供应链攻击、声誉损失 |

不要默认"只有数据泄露才算影响"。资金欺诈、权限持久化、审计失效、成本耗尽都可能是攻击者的真实目标。

## 3 攻击路径

每条路径写成可核对的链路：

```text
画像:   普通用户 B（已登录，知道自己租户 ID）
目标:   读取租户 A 的发票
入口:   GET /api/invoices/:id
已有:   合法会话；ID 为自增整数，可从自己的发票推算
路径:   B -> /api/invoices/123 -> handler 仅校验登录
        -> 查询 WHERE id = ?（无 tenant_id 谓词）-> 返回 A 的发票
缺失:   对象级授权 + 租户谓词（routes/invoices.js:31）
升级:   结合 /api/invoices/export 批量拉取（同一缺失）
前置:   登录；目标 ID 存在
代价:   低（单请求、无交互、无明显告警）
检测:   无审计日志（L12）
```

规则：

- 每一跳都要有 file:line 或可复核的配置证据。
- 区分"已具备"与"需要额外条件"；条件不现实时降级。
- 写清攻击者**不需要**什么（不需要管理员、不需要用户交互），这决定了优先级。
- 路径成立但暴露未知时，标 `needs-runtime`，不写成已确认。

## 4 攻击树与链式升级

单点结论先放进攻击树，再判断价值：

```text
目标: 获取云凭据
├─ 路径 A: SSRF -> 元数据服务 -> 临时凭据
│  ├─ 条件: 可发起任意 URL 请求
│  ├─ 条件: 出网可达元数据地址
│  └─ 条件: 响应可回显或可外带
├─ 路径 B: 仓库密钥 -> 仍有效且权限足够
└─ 路径 C: CI 工作流 -> 读取生产密钥
```

每个节点问"还差什么"。缺一个条件就不是 confirmed，但可以作为 lead 保留。

常见链式方向（与语言无关，以下只是示例；目标出现新链式方向时新增）：

- 信息泄露 → ID/租户枚举 → 越权读取 → 批量导出。
- SSRF → 云元数据/内网服务 → 凭据 → 横向移动。
- XSS → 管理员会话 → 配置修改/权限提升。
- 上传 → 可执行路径 → 代码执行。
- 依赖/构建 → 产物 → 生产环境。
- 低权写 → 批量赋值/角色字段 → 提权。
- 日志/错误泄露 → 内部结构 → 更精准的注入或越权。

链式判断要求每一环都有证据；不能把"可能可以"串成"确认可以"。

## 5 每个入口的滥用用例

对 surface map 的每个入口，尝试写 3–5 条：

> 作为 `<画像>`，凭借 `<已有能力>`，我可以对 `<对象>` 执行 `<动作>`，因为 `<控制缺失/可绕过>`，从而 `<影响>`。

写不完整的，说明证据不足：回到排查，不要先写成 finding。写出来但攻击者本来就有权做的，删掉。

## 6 从攻击者角度定优先级

| 维度 | 问题 | 对优先级的影响 |
| --- | --- | --- |
| 成本 | 需要登录？需要交互？需要枚举？有无限流/告警？ | 成本越低越高 |
| 收益 | 得到什么？一个对象、整个租户、全量、基础设施？ | 范围越大越高 |
| 可重复 | 一次能批量做吗？能否自动化？ | 可批量越高 |
| 隐蔽性 | 是否留痕？是否触发告警？ | 越隐蔽越高 |
| 可升级 | 能否链到更高权限/更大范围？ | 有升级路径越高 |
| 前置条件 | 需要特定配置、竞态窗口、内部位置？ | 条件越苛刻越低 |

优先级不是漏洞类别的属性，是**这条路径对这个攻击者的价值**。

## 7 思考提示

- 如果我是匿名用户，哪个入口最先泄露信息？
- 如果我是普通用户，哪个对象 ID 最容易替换？换完之后能看到什么？
- 如果我只能发一个请求，打哪里收益最大？
- 如果我已经有一个低危问题，下一步能换到什么？
- 哪个假设最脆弱：网关一定拦截？ID 不可枚举？内部服务不可达？日志一定有人看？
- 防守方最不可能监控哪条路径？
- 哪些业务规则可以被滥用而不触发技术告警（退款、优惠、邀请、试用、导出）？
- 哪些"正常功能"组合起来会变成攻击能力？

## 8 常见误区

| 误区 | 纠正 |
| --- | --- |
| 从漏洞名出发 | 从攻击者目标与已有能力出发 |
| 只看单点 | 放进攻击树，看能否链式升级 |
| 把"需要登录"自动降为低危 | 普通用户往往就是最大攻击面 |
| 忽略业务逻辑与多租户 | 设计缺陷通常不在扫描器覆盖内 |
| 忽略内部人与服务账号 | 合法权限的滥用同样需要审计 |
| 只查已知 CVE | 已知漏洞只是路径之一，设计缺陷更常见 |
| 假设攻击者按你设想的路径走 | 找最便宜、最不显眼的路径 |
| 把防御建议当攻击路径 | 建议不是证据，路径要能复现 |

## 9 输出

报告中的 P0/P1 必须附攻击路径（画像、目标、入口、缺失控制、前置条件、影响、检测）。P2/P3 可以是单点，但也要写清"为什么没有被升级"。

攻击路径不是叙事装饰：它是把零散 finding 组织成可处置风险的结构。多条 finding 共享同一路径时，合并为一条主 finding，其余作为影响范围或前置条件。
