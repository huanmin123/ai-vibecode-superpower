# 系统文档与命令路由

- 已设置 `CODEX_HOME` 时全局文档以其为基准，否则用展开后的 `~/.codex/`；不得解析到项目 `docs/`。
- 执行系统命令前读[全局文档入口](~/.codex/docs/README.md)，一次识别本机系统、Shell 和架构，再按需读平台规范。
- Windows 本机命令读 [Windows 与 PowerShell 7](~/.codex/docs/system/windows.md)；macOS 本机或远端命令读 [macOS](~/.codex/docs/system/macos.md)；Linux 本机或远端命令读 [Linux](~/.codex/docs/system/linux.md)。
- SSH、SCP、SFTP 或 rsync 还须读 [SSH](~/.codex/docs/system/ssh.md) 和目标系统文档；本地与远端 Shell 分开构造、转义和验证。
- 文本搜索必须使用 `rg`；缺失时按 [ripgrep](~/.codex/docs/system/rg.md) 和系统文档安装验证。命令语法、工具安装和排障只放系统文档。

## 主要沟通语言

1. 默认使用简体中文与用户沟通，并使用简体中文编写项目文档、设计、计划、复审和面向维护者的说明。
2. 保留代码、命令、文件路径、配置键、环境变量、协议字段、模型 ID、skill 名称和外部产品术语的原文；需要解释时在其后用中文说明作用。
3. 用户明确使用其他语言、外部接口要求特定语言，或原始文本的精确措辞具有契约意义时，遵从该要求，不做机械翻译。

## 用户可理解的沟通与设计表达

1. **结论先行**：先说明结论或当前状态，再给出用户可核对的对象、证据、重要限制和下一步；省略重复、泛泛客套和无关背景。
2. **事实与判断分开**：用具体对象、行为和条件表达；明确哪些是事实、判断、决定和未解决问题，不把假设或实现者自述当作结论。
3. **设计以可观察结果表达**：说明目标与非目标、用户或系统会看到的行为、关键取舍、重要风险、验收标准和验证方式；只在会影响决策时展开实现细节。
4. **需要选择时给出可执行建议**：说明选项差异、推荐及理由，并提出能推进工作的具体问题。

## 开发规范

以下规则定义跨项目的工程质量门；平台命令、领域架构和项目专有流程由各自的权威文档说明，不在此重复。
1. **未知不得静默降级**：无法证明替代路径与原行为兼容时，不得自动 fallback、吞掉错误或报告成功。保留原始错误、已尝试操作、受影响范围和缺失条件，让问题可见、可复现、可修复。
2. **fallback 必须已知且可观察**：只有用户或既有契约明确允许、兼容性已验证的替代方案才能使用；必须说明实际走了哪条路径及其验证证据。
3. **以证据而非猜测决策**：区分已知事实、当前判断和未证实点。需求、设计、行为或根因不明确时，不自行补全为确定结论。
4. **按完整工作单元验证**：完成一个模块或功能后运行最贴近改动的检查，再按影响扩大。记录通过项、未验证项、实际错误和残余问题。
5. **复杂开发使用 `$orchestrate-model-workflow`**：开发、实现、修复、整理、复杂开发、架构设计、漏洞或 Bug 探索、按方案实施、复审和复审后修复应使用该 skill，由其路由取证、实施、复审和验收；交付时说明实际改动、验证证据与未解决问题。
