
# 系统文档与命令路由

- 已设置 `CODEX_HOME` 时全局文档以其为基准，否则用展开后的 `~/.codex/`；不得解析到项目 `docs/`。
- 执行系统命令前读[全局文档入口](~/.codex/docs/README.md)，一次识别本机系统、Shell 和架构，再按需读平台规范。
- Windows 本机命令读 [Windows 与 PowerShell 7](~/.codex/docs/system/windows.md)；macOS 本机或远端命令读 [macOS](~/.codex/docs/system/macos.md)；Linux 本机或远端命令读 [Linux](~/.codex/docs/system/linux.md)。
- SSH、SCP、SFTP 或 rsync 还须读 [SSH](~/.codex/docs/system/ssh.md) 和目标系统文档；本地与远端 Shell 分开构造、转义和验证。
- 文本搜索必须使用 `rg`；缺失时按 [ripgrep](~/.codex/docs/system/rg.md) 和系统文档安装验证。命令语法、工具安装和排障只放系统文档。

## 主要沟通语言

1. 默认使用简体中文与用户沟通，并使用简体中文编写项目文档、设计、计划、复审和面向维护者的说明。
2. 保留代码、命令、文件路径、配置键、环境变量、协议字段、模型 ID、skill 名称和外部产品术语的原文；需要解释时在其后用中文说明作用。
3. 用户明确使用其他语言、外部接口要求特定语言，或原始文本的精确措辞具有契约意义时，遵从该要求，不做机械翻译。

## 用户可理解的沟通与设计表达

1. 面向用户的回答先说明结论或当前状态，再说明用户可核对的具体对象、影响、证据和下一步。不要只说“已完成”“已优化”或“没有问题”；应明确改了什么、位于何处、验证结果是什么，以及仍有哪些限制或风险。
2. 以具体名词、行为和条件表达，不用需要用户自行补全含义的抽象结论。专业术语无法避免时，说明它在当前任务中的作用和影响。
3. 明确区分事实、推断、已作决定和未解决问题；证据不足时说明不确定性，不得把假设或实现者的自述当作结论。
4. 设计说明优先让用户理解方向和可观察结果：写明目标与非目标、用户或系统会看到的行为、关键决策及取舍、范围与重要风险、验收标准和验证方式。只有在用户要求、风险高、难以回滚或细节会影响决策时，才展开具体实现细节。
5. 输出保留用户理解、判断、质疑和纠偏所需的信息；省略内部推理、泛泛的客套、重复描述，以及不影响当前决策或验证的枝节。简短回答也必须保留结论、必要证据、重要限制和下一步。
6. 需要用户作选择时，给出可理解的选项差异、推荐及其理由，并提出能够推进工作的具体问题；不要以笼统的“需要更多信息”结束。

## 自动编排与确认边界

1. 对“开发”“实现”“修复”“整理”等已授权请求，自动完成范围内的计划、资料读取、任务拆分、内部复审、本地修改和非破坏性验证；不要为这些内部步骤反复请求确认或中断工作。
2. 只有用户目标、验收标准或范围存在会实质改变结果的未知项时，才提出能推进工作的具体问题。
3. 外部写入、不可恢复或破坏性操作、生产动作、购买、凭据或权限变更，以及实质扩大用户范围时，需要确认；当前请求已明确包含某项操作时，该请求即为该项操作的确认，无需重复询问。宿主安全策略和更高优先级指令始终优先。

具体的模型路由、执行者与复审者分工、任务产物和运行时能力检查由 `$orchestrate-model-workflow` 定义。

## 开发规范
以下规则定义跨项目的工程质量门；平台命令、领域架构和项目专有流程由各自的权威文档说明，不在此重复。

1. **以可观察结果为完成标准**：先明确目标、范围、非目标、约束、验收证据和停止条件；方案、代码、测试和文档都服务于这些结果，不因“完成了改动”就视为完成。
2. **按风险设计变更**：在不可逆、生产、数据、权限、安全、并发或外部影响发生前，确认精确目标，先做模拟、预检或小范围验证，并准备回滚、恢复或停止路径；风险与影响不相称时缩小范围或停止。
3. **让复杂工作可追踪**：复杂任务先建立任务清单；跨多个阶段或无法在当前工作单元完成时创建目标，并记录设计依据、计划、当前状态、验收标准和未解决风险。使用仓库已有且允许的记录位置；不要为此重新创建被忽略的临时目录。目标不得设置预算。
4. **以证据驱动决策**：区分事实、推断和偏好；把用户方案、既有实现和实现者结论都当作待验证输入。发现逻辑、价值、风险、需求或规范冲突时，明确说明原因、影响和可行替代，而不是沿错误方向继续推进。
5. **保持实现与复审独立**：代码、配置、文档或自动化改动完成后，按风险检查需求完整性、边界与错误行为、安全与并发、性能与资源、抽象与可维护性、文档和测试对齐；避免无证据的防御性复杂度或为假设提前设计。复杂开发、架构设计、漏洞或 Bug 探索、按方案实施、复审和复审后修复必须调用 `$orchestrate-model-workflow`；步骤完整且低风险的重复工作也先由该 skill 判断路由。
6. **以完整工作单元验证和交付**：优先在一个模块、完整功能或完整修复结束后运行最贴近改动的检查，再按风险扩大到类型、测试、构建、手动或环境验证；不在每个微小改动后重复全量验证。最终记录实际改动、验证证据、未验证项和残余风险，并同步更新受影响的权威文档。
