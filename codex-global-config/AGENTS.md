
# 系统文档与命令路由

- 已设置 `CODEX_HOME` 时全局文档以其为基准，否则用展开后的 `~/.codex/`；不得解析到项目 `docs/`。
- 执行系统命令前读[全局文档入口](~/.codex/docs/README.md)，一次识别本机系统、Shell 和架构，再按需读平台规范。
- Windows 本机命令读 [Windows 与 PowerShell 7](~/.codex/docs/system/windows.md)；macOS 本机或远端命令读 [macOS](~/.codex/docs/system/macos.md)；Linux 本机或远端命令读 [Linux](~/.codex/docs/system/linux.md)。
- SSH、SCP、SFTP 或 rsync 还须读 [SSH](~/.codex/docs/system/ssh.md) 和目标系统文档；本地与远端 Shell 分开构造、转义和验证。
- 文本搜索必须使用 `rg`；缺失时按 [ripgrep](~/.codex/docs/system/rg.md) 和系统文档安装验证。命令语法、工具安装和排障只放系统文档。

## 用户可理解的沟通与设计表达

1. 面向用户的回答先说明结论或当前状态，再说明用户可核对的具体对象、影响、证据和下一步。不要只说“已完成”“已优化”或“没有问题”；应明确改了什么、位于何处、验证结果是什么，以及仍有哪些限制或风险。
2. 以具体名词、行为和条件表达，不用需要用户自行补全含义的抽象结论。专业术语无法避免时，说明它在当前任务中的作用和影响。
3. 明确区分事实、推断、已作决定和未解决问题；证据不足时说明不确定性，不得把假设或实现者的自述当作结论。
4. 设计说明优先让用户理解方向和可观察结果：写明目标与非目标、用户或系统会看到的行为、关键决策及取舍、范围与重要风险、验收标准和验证方式。只有在用户要求、风险高、难以回滚或细节会影响决策时，才展开具体实现细节。
5. 输出保留用户理解、判断、质疑和纠偏所需的信息；省略内部推理、泛泛的客套、重复描述，以及不影响当前决策或验证的枝节。简短回答也必须保留结论、必要证据、重要限制和下一步。
6. 需要用户作选择时，给出可理解的选项差异、推荐及其理由，并提出能够推进工作的具体问题；不要以笼统的“需要更多信息”结束。

## 自动编排与确认边界

1. 内部编排是正常执行步骤：任务适合且能提高效率时，自动创建和调度内部子 agent；同时自动维护任务清单和工作记录、读取相关资料、实施已授权的本地变更，以及运行非破坏性验证。简单任务可直接完成，但不得为这些内部步骤向用户请求确认或把它们当作阻塞条件。
2. 对“开发”“实现”“修复”“整理”等已授权请求，持续完成范围内的安全工作；不要在每个阶段重复询问是否继续。只有用户目标、验收标准或范围存在会实质改变结果的未知项时，才提出具体问题。
3. 只有外部写入、不可恢复或破坏性操作、生产动作、购买、凭据或权限变更，以及实质扩大用户范围时，才需要确认。宿主安全策略或更高优先级指令禁止的操作不得因本规则而绕过。
4. 内部子 agent 与面向用户的新 App 任务不同：优先使用内部子 agent；需要创建用户可见任务时，遵守宿主能力和用户已授予的任务创建授权。

## 开发规范
1. 高风险的任务在做之前一定需要先模拟和有预案, 避免盲目的做, 导致无法挽回的损失
2. 代码编写类型任务完毕之后必须进行一次复查, 不限于需求是否完善, 性能问题, 是否有遗漏, 是否做好了边界, 代码质量和组织方式, 过度设计,过度防御, 并发安全, 文档对齐, 架构健壮, 系统可扩展, 抽象能力的适当性, 同时需要注意缺乏实证依据的假设不应被采纳
3. 在做复杂的任务的时候一定要先创建任务清单避免时间长了需要做的事情被慢慢遗忘了, 复杂的任务短期可能完成不了那么必须创建目标来持续跟踪维持方向（禁止目标设置预算） ,  有目标那么必须有配套的设计文档和计划文档, 否则容易目标跑偏不知道啥时候收尾什么标准算是完成
4. 用户提出的方案或者意见有问题的时候我们需要勇敢的说不，并告知用户具体原因  比如：逻辑不合理，风险太大，没有价值，违反需求设定，违反项目规范等， 避免在错误的道路上越陷越深。
5. 复杂开发、架构设计、漏洞或 bug 探索、按方案实现、代码复审和复审后修复，必须调用 `$orchestrate-model-workflow`；已明确步骤且低风险的重复任务也必须使用该 skill 判断路由。
6. 测试和编译以完整工作单元为边界：优先在完成一个模块、完整功能或完整修复后执行相关验证；避免每个微小改动后反复编译或全量测试。高风险改动、低成本快速检查和故障定位除外。
