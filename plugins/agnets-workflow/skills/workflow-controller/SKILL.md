# 工作流控制器

需要持久化 DAG 调度、可恢复交接或可强制执行的总体验收记录时使用此 skill。简单问答、只读查询和边界清晰的单文件低风险任务不初始化控制器，由 main/root 直接完成并做最终验证。控制器管理状态和关闭关卡，不替代 Codex 原生代理工具。总审 completion 必须由控制器绑定并最终回写；制品写入失败时节点保持运行中，原 claim 可重试。

## 必经流程

1. 创建 JSON 任务清单，包含 `task_id`、绝对路径 `workspace`、`goal`、唯一的 `requirements` 和 DAG `nodes`。可选 `workspace_claims` 是非空数组，元素精确为 `{mode:"read"|"write",prefix:"workspace-relative POSIX segment prefix"}`；缺失按根目录 `write` 兼容。控制器规范化排序、去重并拒绝绝对/逃逸/链接穿越及指纹忽略目录；读/读 可重叠，任一写入与相同或祖先/后代范围冲突，`.` 与全部范围冲突。一份清单对应一次完整用户任务；取证、设计、实现、集成和节点测试均是内部节点，`quality_guard` 只定义节点验证证据，不是审核节点。节点必须包含 `id`、`kind`、可选 `agent_type`、可选 `depends_on`（默认为空数组）、`execution_risk`、`routing_reason`、`execution_owner`、`integration_owner` 与 `quality_guard`。`routing_schema_version=1` 保持严格兼容：唯一 `total_review` 直接依赖所有其他节点。新流程使用 `routing_schema_version=2`，除抽象的 `assurance_level` 外还必须带 `assurance_assessment`；`impact`、`recoverability`、`uncertainty`、`verifiability`、`coupling` 各自必须精确包含 `status`、非空 `evidence` 数组和 `rationale`，另带 `selection_reason`。`status` 只取 `controlled`、`partial`、`unknown`：全部 `controlled` 对应 `verification`，出现 `partial` 且没有 `unknown` 对应 `terra`，任一 `unknown` 对应 `sol`，控制器拒绝不一致的门级。`verification` 没有审核节点，关闭前必须调用 `workflow_record_verification`；`terra` 有唯一的只读 `quality_review`，初始角色是 `avsp_terra_xhigh`；`sol` 有唯一的 `total_review`，初始角色是 `avsp_sol_high`。唯一审核节点直接依赖全部非审核节点，且没有节点依赖它，因此只会在完整任务结束、工作区冻结后运行。执行期间若证据显示原门级不足，可在审核门被认领前调用 `workflow_raise_assurance`，按 `verification -> terra/sol`、`terra -> sol` 单调提高等级，并显式提供新 reviewer 的 `replacement_agent_task_path` 和真实 `integration_owner`；它是唯一允许的末端门结构调整，通用 `workflow_add_node` 仍拒绝追加。`terra` 的第二次有效 `fail` 会将同一 `quality_review` 原子提升为 `total_review` 并改由 Sol 认领；持久 `assurance_level` 仍为初始 `terra`，派生 `effective_assurance_level` 才变为 `sol`。省略 `agent_type` 时，现代 `read_only`/`delegable` 节点分别默认由 Luna readonly/executor 执行，`total_review`/`quality_review` 分别默认由 Sol high/Terra xhigh 执行；显式 `agent_type` 必须与风险兼容。`execution_risk=read_only` 只用于可证明不改变工作区或外部状态的取证与审核；`delegable` 只用于完整、可恢复且允许委派的写入契约；其余写入为 `protected`。初始化后 DAG 除上述受控末端升级外不可追加。旧清单没有版本标记时可读取，但会被明确标为 legacy/protected，不能授权 Luna executor。为任务固定一个绝对路径 `state_dir`，通常是 `<workspace>/.codex/workflow-controller`；同一任务的每一次 MCP/CLI 调用都必须携带完全相同的绝对路径。若初始化进程在返回前中断，使用 `workflow_reconcile_workspace(workspace, task_id, state_dir)`；兼容旧调用只在 registry 中唯一 initializing entry 时可无歧义处理。每条需求包含唯一的 `id` 和非空 `text`。
2. 调用 `workflow_init`，再调用 `workflow_ready`。对每个返回节点，main/root 必须先用 `spawn_agent` 创建新的原生实例，核对返回的真实任务路径和 role，并在任务包中要求该实例在自己实际开始首个回合后，以其真实路径、role 和 `native_agent_started=true` 调用 `workflow_start` 原子认领并激活节点；Root 不得替它调用 start。`workflow_claim` 仍保留给需要先登记、再由代理握手的兼容场景。若计划实例在认领前未启动，确认其已停止后调用 `workflow_rebind_pending` 把未认领的现代 pending 节点换绑到新的真实任务路径，不消耗一次执行 attempt。不得先 claim 再用 `followup_task` 唤醒历史实例，也不得把 followup 提交成功当成实例已启动。运行中的代理仍须定期调用 `workflow_heartbeat`；`workflow_checkpoint` 也会刷新一次租约心跳。不得因为等待一个相互独立的就绪节点而延迟派发其他节点。
3. 运行中的代理定期调用 `workflow_heartbeat`，并在开始、每个重要进展和阻塞前把不超过 32 KiB 的 JSON 进度写入临时文件后调用 `workflow_checkpoint`。checkpoint 应说明已完成步骤、下一步、改动/证据路径、验证和阻塞。心跳仅覆盖节点的最后活动时间和计数，不追加事件历史；每个原生子代理进入 `AgentStatus::Completed`（宿主可能显示为 `FINAL_ANSWER`）后，main/root 才能将结构化结果写入 JSON 文件，并携带匹配的 `claim_id` 与 `completion_attestation=native_agent_finished` 调用 `workflow_complete`（仅可用 `succeeded`、`failed`、`blocked`、`skipped` 或 `unavailable`）。唯一的常规例外是已由 `workflow_rescue` 显式转交、且当前 `agent_role=main/root` 的节点：Root 在完成自身验证后以 `completion_attestation=root_rescue_self_completion` 结束，控制器会留下该例外的审计记录，不能归为 Luna 结果。Sol CLI 的 `total_review` 若以 `unavailable` 结束，则仅在已确认子进程退出时记录 `completion_attestation=native_agent_exit_confirmed`，子进程未启动时记录 `native_agent_start_failed`；只有未收到 `spawn` 事件就报错才属于后者，启动后 error 必须等到实际 exit 才能算已确认退出。有效 Sol 结果文件会保持 `workflow_completion.state=pending`；main/root 必须把同一 `outcome.json` 作为 `workflow_complete` 的 `result`，控制器在持久化完成状态后原子回写最终状态，恢复时必须向控制器核对 claim 终态。两类异常 attestation 都明确不是最终 `Completed`。消息、`wait_agent` 返回或 `send_message` 投递都不是最终状态。失败或阻塞节点必须保持可见；不得将其标为成功来解锁依赖节点。
4. 出现未激活、心跳过期、中断恢复、锁阻塞、迁移、诊断、隔离或清理时，先读 [`recovery-and-retention.md`](references/recovery-and-retention.md)，再执行对应工具；没有旧执行者已停止的证据时不得重排队、救援或释放租约。
5. 所有工作节点完成后，main/root 完成验证、清理已知测试产物并调用 `workflow_audit_context` 冻结证据，再进入唯一末端审核门。若尚未开始审核且风险上升，先更新同一结构化 `assurance_assessment` 并调用 `workflow_raise_assurance`，不得为某个小步骤新增审核。`terra` 门的每一次审核都使用从未参与该任务的新建 `avsp_terra_xhigh`；一审 `fail` 后，在任务内部完成修复，写入含 `source_review_claim_id`、`repaired_by`、`addressed_findings`、`verification_evidence` 和当前 `workspace_fingerprint` 的 JSON，再调用 `workflow_record_repair`，才可 `workflow_retry` 进入二审。`addressed_findings` 必须逐项提供 `finding_id`、解决说明和该项验证证据，并覆盖一审全部 blocking finding。修复可以是代码、补证或外部状态处理；记录会标明 `workspace_changed`，不要求指纹必然变化。二审 `fail` 后直接调用 `workflow_retry`，并为新 Sol 提供新的 `replacement_agent_task_path`，不得先进行局部修复。`sol` 门和已升级的 Terra 门把紧凑证据包（包括两轮 Terra 审核和修复记录）交给从未参与该任务的新建 Sol。使用 Sol CLI、受控外部证据或硬超时时，另读 [`sol-review.md`](../orchestrate-model-workflow/references/sol-review.md)。有效 CLI 结果保持 `workflow_completion.state=pending`；记录审核后把同一文件传给 `workflow_complete`，并在恢复时同时核对结果文件和控制器状态。
6. Terra 和 Sol 的审核 JSON 都必须包含 `auditor_task`、`auditor_role`、审核节点的 `claim_id`、`verdict`、`requirement_coverage`、`workflow_snapshot`、`workspace_fingerprint`、`scope_and_regression`、`verification_gaps` 和 `residual_risk`。`fail` 还必须包含至少一个 blocking finding；每项 finding 精确包含唯一、以字母开头且最长 80 字符的 `id`、`severity`、可空 `requirement_id`、`summary` 和 `evidence`。`pass` 不得包含 blocking finding，`unavailable` 不得包含 findings。`workflow_snapshot` 必须原样回填 `workflow_audit_context` 的结果；控制器会核验它仍对应当前非审核节点的状态与结果，并核验该 claim 仍属于同一路径、同一角色的运行中审核节点。`verification` 门使用 `workflow_record_verification`，记录必须含 `verified_by`、相同的需求覆盖、快照、指纹和风险字段；完全相同的重复记录幂等，不同内容只能在 `workflow_invalidate_gate` 保留旧记录到有界 `verification_history` 后重记。进入 Sol 后默认使用 `avsp_sol_high`；第一次 high `fail` 修复后仍使用新的 high 实例，第二次连续 high `fail` 后由 `workflow_retry` 自动切换 `avsp_sol_xhigh`；xhigh 修复后再次 `fail` 时，控制器冻结 `max_review_charter` 并把节点置为 `blocked`。Terra 先以 `workflow_record_repair` 覆盖 charter blockers，才可重试为新的 `avsp_sol_max` closure；该 closure 只复核 charter、repair diff/回归与原需求。closure 的新 blocker 只有在 `repair_regressions:[{finding_id,evidence}]` 证明它由本次 repair 引入且 `requirement_id` 指向原 requirements 时才可继续当前闭环；否则控制器记录 `out_of_charter` 并置为 `scope_decision_required`，`workflow_close_check` 拒绝关闭，main/root 或用户必须创建替代任务或显式扩大 charter。旧或缺 charter max 状态一律 fail-closed。`unavailable`、超时、证据不足和无效输出不触发 Terra 或 Sol 升级；每个节点最多有 8 次普通执行预算与额外 8 次不可用预算，后者不占用前者；仅在选定 Sol role 或模型确实不可用时使用 `avsp_terra_xhigh_readonly`。
7. 审核代理调用 `workflow_record_review` 并进入原生 `AgentStatus::Completed`（宿主可能显示为 `FINAL_ANSWER`）后，main/root 以审核 claim 的 `completion_attestation=native_agent_finished` 调用 `workflow_complete`，再调用 `workflow_close_check`。`verification` 门由 main/root 记录结构化验证后直接调用 `workflow_close_check`。只有 `close_allowed` 为 true 才能报告成功或触发发布；通过时控制器才释放该工作区租约。末端关卡记录后、关闭前若非审核任务状态或工作区变化，关闭检查会使旧记录失效；main/root 必须调用 `workflow_invalidate_gate`，对 `verification` 清除旧记录后重新验证，对 Terra/Sol 以新的独立 `replacement_agent_task_path` 重开同一个审核节点，再基于新快照完成关卡。不得复用旧 `pass` 或追加第二个审核节点。

## 控制器边界

- `total_review` 的 finalized outcome 只能在同一 claim 已持久化 completion intent 后恢复；intent 保存的结果摘要必须与制品除 `workflow_completion` 外的内容一致。没有 intent、摘要不匹配或只提交调用方伪造的 `completed=true` 制品都会被拒绝。`quality_review` 不产生 Sol completion envelope，但两类审核节点都只有当前 claim 已记录 `pass` 才能以 `succeeded` 完成；`fail` 应以 `failed` 完成，`unavailable` 保持既有恢复语义。只有节点最终以 `failed` 完成的 Terra `fail` 才计入两次 Terra 升级阈值；第一次有效 Terra `fail` 对应的修复记录是二审的前置条件，第二次有效 `fail` 直接升级 Sol。已进入 Sol 的 `fail` 才参与 high -> xhigh -> max；`unavailable`、超时、无效输出或其他完成状态不会计入。

- 控制器记录由代理提供的任务路径和 claim；它不能验证真实 Codex 身份，也不能自行调用 Codex 协作 API。`workflow_start` 的 `native_agent_started=true` 与 `workflow_complete` 的 `completion_attestation` 是持久化审计声明，不是不可伪造的宿主认证；前者必须由已开始回合的原生实例提交，普通后者只能由 Root 在确认该实例进入原生 `AgentStatus::Completed` 后以 `native_agent_finished` 提交。只有显式 Root 救援节点能使用 `root_rescue_self_completion`，并会记录为救援而非 Luna 完成；Sol CLI 在 `total_review` 以 `unavailable` 结束时，依据已确认的子进程退出或启动失败分别记录 `native_agent_exit_confirmed` 或 `native_agent_start_failed`，两者都不表示最终答复。`claim_id` 防止误完成和误接管，不构成认证或权限边界。对 `quality_review` 与 `total_review`，控制器都要求该 claim 至少有一次 `workflow_heartbeat` 才能记录审核；这只能证明工作流实例执行过启动握手，不能替代原生身份认证。
- `read_only` 节点只允许配置的只读 role（常规证据优先 Luna）；`avsp_luna_high_executor` 与 `avsp_luna_xhigh_executor` 只能认领完整、`delegable` 且 `execution_owner` 等于其真实任务路径的节点。`*_writer` 是兼容角色；新任务默认使用 executor，显式使用 writer 时必须与节点的 `agent_type` 精确匹配。非审核 `protected` 节点或 legacy 路由必须交由 Terra 处理；`quality_review` 只允许 `avsp_terra_xhigh`，`total_review` 按 Sol 总审规则处理。每次 v2 审核重试都必须声明此前未参与任务的新 `replacement_agent_task_path`。Root 救援只能通过 `workflow_rescue` 显式进入 `main/root` 路由，并保留原 Luna attempt。控制器不证明写入目标是否真实互斥，协调者仍须在派发前核验。
- `workflow_ready` 只是调度建议。main/root 仍是唯一能创建原生代理树的主体，且必须保持现有 role 拓扑。
- MCP 默认压缩高频调度响应，只返回继续调度所需的节点、claim、租约、路由和状态摘要；`effective_assurance_level` 与紧凑验证摘要也会返回。CLI 输出、`workflow_audit_context`、恢复包与 `workflow_doctor` 保持完整。协调者先从 `workflow_status` 取得 `cursor`，再调用 `workflow_wait` 被动等待 ready、终态、stale、审核或验证记录变化；普通 heartbeat 不改变该游标。同一 MCP 服务对同一任务只允许一个活动 wait。仅在排障或审计确需参与者、完整结果和审核记录时使用 `workflow_status detail=full`，不得用固定短间隔重复查询状态。
- 新节点默认有 600 秒激活窗口，运行租约默认 1,800 秒；`workflow_start` 会原子记录首个激活心跳，`workflow_checkpoint` 也会刷新租约。它们不是总运行时限，持续活动的长任务可以继续运行。
- `state_dir` 是必填的绝对路径。控制器、MCP wait 和 Sol CLI 会按现有物理祖先规范化它，Windows 大小写、junction 与 symlink 别名共享同一个状态、锁、wait 和总审结果目录；推荐使用 `<workspace>/.codex/workflow-controller`，不要把它纳入源代码控制差异，也不要删除活动任务的状态文件。
- 每个工作区在 `.codex/workflow-controller/workspace-lease.json` 中持有 `active_tasks` registry；workspace 根级 authority 持久绑定控制目录和当前 registry 文件对象，所有活动任务 mutation 使用 `authority -> registry -> task state` 锁序并在操作前后复核物理身份。范围不冲突的多个任务可并行，旧/缺失 claims 一律根目录 `write` 独占；曾初始化后的 registry 缺失或文件对象替换必须失败，不能按空 registry 重建。claims 生命周期不可原地修改；扩大范围必须确认旧执行者停止、释放自身 entry，再以 claims 超集和新 `task_id` 初始化替代任务。它是协调声明而非 ACL：末端 `scope_and_regression` 必须核验实际 diff/产物均属于 `write` claims，无法证明不得 pass；共享或全局副作用使用根目录 `write` 独占。租约释放后，旧任务只可读取，不能再认领、重试、追加节点、写心跳、完成或记录审核。
- `agent_thread_id` 仅在宿主实际提供时记录。控制器不能读取 Codex 私有状态或直接恢复原生代理；恢复语义与 SQLite/租约维护见 [`recovery-and-retention.md`](references/recovery-and-retention.md)。
- 工作区指纹覆盖 read/write claims 的并集、绑定规范 claims，并为缺失 prefix 记录 marker；范围外 peer 写入不会使质量门失效，范围内或 read claim 的变化会失效。指纹继续排除 `.git`、`.codex`、`node_modules`、`.venv`、`.yarn` 与 `.yarn-cache*`；构建输出仍属于审核范围。清单最多 64 个节点与 64 条需求；每个节点最多 8 次普通执行尝试，另有最多 8 次 `unavailable` 尝试，二者分别计数。节点结果最多 64 KiB、审核或修复记录 JSON 最多 128 KiB。完整日志应作为外部制品保留，状态中只写摘要和可核对路径。
