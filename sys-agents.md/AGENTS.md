
# 系统文档与命令路由

- 已设置 `CODEX_HOME` 时全局文档以其为基准，否则用展开后的 `~/.codex/`；不得解析到项目 `docs/`。
- 执行系统命令前读[全局文档入口](~/.codex/docs/README.md)，一次识别本机系统、Shell 和架构，再按需读平台规范。
- Windows 本机命令读 [Windows 与 PowerShell 7](~/.codex/docs/system/windows.md)；macOS 本机或远端命令读 [macOS](~/.codex/docs/system/macos.md)；Linux 本机或远端命令读 [Linux](~/.codex/docs/system/linux.md)。
- SSH、SCP、SFTP 或 rsync 还须读 [SSH](~/.codex/docs/system/ssh.md) 和目标系统文档；本地与远端 Shell 分开构造、转义和验证。
- 文本搜索必须使用 `rg`；缺失时按 [ripgrep](~/.codex/docs/system/rg.md) 和系统文档安装验证。命令语法、工具安装和排障只放系统文档。

‌# 开发规范
1. 子agent在合适的时候就可以主动创建, 但是需要合理安排, 避免简单的事情变得更为复杂, 除非和主agent没有冲突并且能提高主agent的效率那么可以考虑
2. 高风险的任务在做之前一定需要先模拟和有预案, 避免盲目的做, 导致无法挽回的损失
3. 代码编写类型任务完毕之后必须进行一次复查, 不限于需求是否完善, 性能问题, 是否有遗漏, 是否做好了边界, 代码质量和组织方式, 过度设计,过度防御, 并发安全, 文档对齐, 架构健壮, 系统可扩展, 抽象能力的适当性, 同时需要注意缺乏实证依据的假设不应被采纳
4. 在做复杂的任务的时候一定要先创建任务清单避免时间长了需要做的事情被慢慢遗忘了, 复杂的任务短期可能完成不了那么必须创建目标来持续跟踪维持方向（禁止目标设置预算） ,  有目标那么必须有配套的设计文档和计划文档, 否则容易目标跑偏不知道啥时候收尾什么标准算是完成
5. 用户提出的方案或者意见有问题的时候我们需要勇敢的说不，并告知用户具体原因  比如：逻辑不合理，风险太大，没有价值，违反需求设定，违反项目规范等， 避免在错误的道路上越陷越深。
6. 复杂开发、架构设计、漏洞或 bug 探索、按方案实现、代码复审和复审后修复，必须调用 `$orchestrate-model-workflow`；已明确步骤且低风险的重复任务也必须使用该 skill 判断路由。
7. 测试和编译以完整工作单元为边界：优先在完成一个模块、完整功能或完整修复后执行相关验证；避免每个微小改动后反复编译或全量测试。高风险改动、低成本快速检查和故障定位除外。
