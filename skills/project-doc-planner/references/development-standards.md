# 开发规范参考

当需要创建或更新项目开发规范、根目录 `AGENTS.md`、`docs/architecture/功能开发指导.md`、`docs/architecture/问题修复指导.md`、`docs/architecture/大文件重构指南.md`、前端/后端规范、存储文档、安全文档或验证文档时，加载本参考。

只借鉴成熟项目里的规范组织方式和规则颗粒度，不复制具体业务事实、命令、模块名、供应商、数据库名、账号模型或业务流程。凡是无法从当前项目确认的信息，写成占位符或 `待确认`。

## 基线原则

- 优先完成一个轻量、完整、可验证、可维护的闭环。
- 新增结构前先读现有文档和代码边界，不直接新增平行体系。
- 长期稳定事实写入架构、功能、开发或部署文档；临时执行选择写入 `plans/`。
- 默认按当前最优实现推进：当前 schema、当前 API 契约、当前 UI 流程、当前项目约定。
- 除非用户明确要求，或项目既有指令强制要求，否则不做向下兼容。
- 禁止把双读、双写、启动迁移、临时同步、兼容兜底、迁移标记或一次性数据修复写入正常运行路径。
- 既有数据处理应作为明确的离线 SQL、离线脚本或重建步骤；只有用户要求时才提供，并且不保留为长期运行时代码。
- 如果确实需要兼容，必须记录兼容范围、来源约束、退出条件和验证证据。

## 环境资源与上下文规范

- 公开 `docs/` 负责规则、模板、门禁和通用流程；真实开发、测试、生产运行事实放在 `.local/project-resources/` 或项目指定的 Git 忽略私有目录。
- 私有资源按 `dev/`、`test/`、`prod/` 分区。Agent 默认读取 `dev/`；生产操作前必须显式切换到 `prod/` 上下文，并获得用户明确确认。
- `test` 没有独立环境时，可以声明复用 `dev`，但必须在 `test/README.md`、`test/env/README.md` 和环境加载脚本中写清实际 env、数据库、缓存/队列、namespace 和未来拆分条件。
- 每个环境至少维护 `README.md`、`env/README.md`、`database/README.md`；生产还应维护 `deploy/`、`logs/`、`runbooks/` 和 `releases/`。
- 真实 `.env`、账号、密码、token、连接串、数据库备份、发布私有包和事故材料必须被 `.gitignore` 忽略，不进入提交、公开文档、发布包说明、截图或最终回复。
- 修改真实 env、数据库、缓存/队列、namespace、域名、反代、守护进程或发布方式后，必须同步对应私有资源 README；若通用规则或模板变化，再同步 `docs/develop` 或 `docs/deploy`。
- 环境加载脚本应把文档规则变成硬门禁：dev/test 加载前检查数据库、Redis DB、namespace、端口、服务名或云资源标签，发现生产目标时拒绝加载。
- smoke、migration、package、deploy 和日志脚本不得输出完整 DSN、Authorization、Cookie、API Key、OAuth token、会话 token、代理密码或数据库密码。
- 生产发布必须有版本化 release 目录，建议格式 `YYYY-MM-DD_NNN`，至少包含产物、发版说明、校验和和回滚步骤；当前线上版本用 `current-release.txt` 或等价机制记录。

## AI 交付流水线规范

- 项目应把常见用户指令映射到固定执行流：开发/修复、发测试、上线、回滚、线上排查、补发版记录。
- 每条执行流必须包含入口文档、目标环境、自动化脚本、预检门禁、成功证据、失败停止条件和记录位置。
- 开发流：读文档、写/更新计划、实现、运行本地验证、更新相关 docs/bug/refactors。
- 测试发布流：加载 test 或 dev 隔离 env、执行迁移或部署、运行 smoke、记录测试验证结果。
- 生产上线流：生产预检、构建包、校验包内容、备份 env/数据库/缓存/当前 release、准备 rollback、明确确认、部署、smoke、记录 release 和观察窗口。
- 回滚流：读取 current release 和目标 rollback，评估数据影响，执行切回，运行 smoke，记录回滚结果。
- 线上排查默认只读；涉及写生产、重启服务、迁移、清理缓存、改配置或回滚时必须升级为确认动作。
- 若项目允许无人值守上线，必须额外记录预授权边界、允许分支、时间窗口、变更类型、最大影响范围、自动回滚阈值、通知渠道和审计要求。默认不要无人确认改生产。

## 功能开发规范

- 编码前先划分变更范围：前端页面、API 请求层、后端路由、服务层、repository/storage、脚本、配置、文档、验证。
- 先判断是否影响模块边界、数据结构、API 入参/出参、默认值、敏感字段、权限、错误语义或验证方式。
- 路由/控制器只处理协议边界；service 承接业务规则和副作用；repository/storage 承接 SQL、行映射、事务和当前 schema；前端页面承接组合、展示和交互。
- 保持单一事实来源。前端可以改善输入和展示，但业务事实、默认值、权限和最终校验由后端/存储收口。
- 新字段必须说明含义、默认值、可空性、敏感性、展示策略、索引/查询影响和当前 schema 处理方式。
- API、前端类型、后端类型、存储行、校验和文档必须同步变更。
- 不为单个窄功能引入重型框架、复杂全局状态、大型抽象或并行体系。
- 外部请求、凭据处理、数据写入、后台任务、导入导出、审计和日志等副作用应放在 service、脚本、worker 或有界队列中。
- 面向人阅读的错误、日志、空态、提示和说明遵循项目语言；协议字段、枚举值、路由路径、header、缓存 key、SQL 常量和外部事件名不翻译。

## 问题修复规范

- 先把问题还原为可观察现象：现象、触发入口、期望行为、实际行为、影响范围、复现稳定性和环境。
- 改代码前先追完整触发链路。前端至少追到页面/组件状态、API 请求和后端响应；后端至少追到 route、校验、service、repository/storage 或外部依赖。
- 在正确层级修根因，不用刷新、等待、重复请求、删除数据、大范围条件分支或吞错误来掩盖问题。
- 文档和代码不一致时，先判断是代码偏离设计，还是文档过期，再更新对应产物。
- 必查相邻路径、类型、字段、权限、空/加载/错误/禁用态、敏感字段边界、脚本和文档入口。
- 有复用价值、容易复发、定位成本高或影响共享层的问题，记录到 `docs/bug/`，使用稳定 `BUG-0001` 形式编号，写清根因、修复、验证、复发预防和关联问题。

## 重构规范

- 拆分前先确认当前行为基线。
- 一次只拆一个清晰职责边界，不混入无关新功能、样式调整或行为变化。
- 优先抽类型、常量、formatter、validator、mapper、默认值构造、表格列配置和 payload 构造，再处理高风险副作用。
- 新文件命名必须表达职责，避免 `utils2`、`helperNew`、`misc` 这类模糊名称。
- 如果重构必须改变行为，要说明保留的当前模型、删除的过时路径和验证证据。
- 有复用价值或跨层的大文件/模块重构，记录到 `docs/refactors/`，使用稳定 `REFACTOR-0001` 形式编号，写清重构前后职责、行为边界、验证、风险和经验。

## 前端规范

- 管理后台、SaaS、CRM、运维和运营类工具优先追求信息密度、可读性、重复操作效率、状态清晰和维护成本低，不做营销页式视觉。
- 优先使用现有 UI 库和全局样式，不为单个页面手写基础组件。
- 页面结构保持稳定：页面容器、标题/上下文、工具栏、筛选/操作区、主体列表/表单/内容、弹窗或抽屉。
- 列表必须考虑加载态、空态、错误态、禁用态、长文本、横向溢出、复制入口、操作列稳定位置、分页/加载更多，以及必要的移动端形态。
- 同类控件跨页面重复出现时，应抽为通用列表、工具栏、操作、选择器或状态组件；页面私有组件先放在页面附近，稳定复用后再上移。
- 颜色和图标只能辅助表达，关键状态必须有可读文字。
- 避免多层卡片嵌套、超大装饰标题、大面积渐变和工作台里的营销页式排版。
- 敏感值不能通过列表、缓存筛选、本地存储、截图、日志或复制文案泄露。
- 前端改动至少按范围运行类型检查；涉及布局或响应式时补视口和交互检查。

## 后端、存储与运行时规范

- API route 保持轻量：解析、校验、鉴权、调用 service、返回统一响应。
- service 负责业务规则、外部请求、副作用和流程编排。
- repository/storage 负责 SQL、行映射、事务和当前 schema。
- schema 文件只描述当前完整结构。禁止运行时探测旧列、旧表改名、启动升级模拟或临时数据同步。
- 列表查询必须稳定排序：业务排序字段后追加不可漂移的唯一兜底字段。
- 请求路径和列表路径必须有边界：禁止无界全表扫描、深 offset、全量补数、全 ID fanout，或在分页窗口足够时强做精确总数。
- 大文件、日志、审计 payload、导入导出和频繁读取的数据必须使用 offset、cursor、stream 或窗口读取。禁止为了搜索、分页、追尾或切片把完整文件读入内存。
- 业务统计、额度、TopN、趋势和摘要应读取预聚合表、窗口表或缓存。禁止在请求路径临时 `SUM/GROUP BY`，也禁止前端对原始事实 `reduce` 出业务汇总。
- 后台任务、批量写入、保留期清理、审计、日志索引和维护任务应放入 worker/job 进程或有界队列。
- 队列必须有条数或字节上限、丢弃/拒绝/合并策略、错误日志和重试边界，不能无限阻塞已经可返回的用户请求。
- 运行配置变化必须同步配置示例、开发文档、部署文档和验证说明。
- 生产/维护脚本必须说明会影响哪些数据；按需要支持 dry run 或安全验证路径；不得接入正常请求路径或启动路径。

## 安全与日志规范

- 新数据先分级：凭据/token/密码、高敏摘要、业务敏感请求/响应内容、普通运维元数据。
- 凭据按需加密或哈希保存。禁止记录完整 API Key、OAuth token、会话 token、代理密码、登录密码、Cookie、Authorization header。
- 列表和摘要只展示掩码、前缀、状态或安全元数据，不展示完整凭据。
- 请求/响应快照必须有大小上限、脱敏、权限控制和截断标记；脱敏失败时宁可丢弃快照，也不能保存原文敏感数据。
- 完整原始 payload 捕获只能作为高权限审计能力存在，不能写入普通日志或使用记录。
- 操作日志只记录成功的状态变更、操作人、目标、安全字段差异、trace ID 和影响范围；只读查询不写操作日志。
- 日志必须包含 trace ID 和结构化事件名；错误应保留可读摘要，但不能带敏感 payload。
- 使用记录、审计 payload、操作日志、运行日志、统计、监控和缓存必须有明确保留与清理策略。

## 验证与交付规范

- 测试项应在计划或实现过程中明确，不要只在最后写“已验证”。
- 最低代码验证通常包含类型检查；根据改动范围补构建、单元测试、集成测试、烟测、接口检查、浏览器检查或部署检查。
- 前端改动验证加载、空态、错误、提交、刷新、权限和视口表现。
- 后端/API 改动验证成功路径、失败路径、非法输入、鉴权、错误语义和相邻接口。
- 存储改动验证当前完整 schema 下的新库启动/写入；只有用户要求时才验证离线数据处理方案。
- 脚本改动验证可重复执行、dry run/安全路径、目标路径和失败行为。
- 构建/部署改动验证运行前提、包内容、环境示例、启动脚本、健康检查、常驻进程和回滚/恢复说明。
- 环境资源改动验证 `.gitignore`、env 加载脚本、隔离检查、smoke 输出脱敏、生产 release 目录和回滚材料。
- 交付流水线改动验证意图映射、脚本入口、预检失败行为、生产确认门禁、发版记录和回滚路径。
- AI 最终输出应说明功能范围、主要落点、关键设计、已跑验证、未验证项和剩余风险。

## 文档维护规则

- 功能或流程变化：更新 `functions/`、相关架构文档；需要跟踪时更新 `plans/`。
- API、权限或存储变化：更新契约、存储说明、验证说明和受影响的前后端规范。
- 前端布局、列表、组件或品牌变化：按需更新前端架构、样式、响应式、通用组件或品牌文档。
- 后端分层、job、队列、脚本或运行时变化：按需更新后端规范、后台任务说明、开发/部署文档。
- 有复用价值的 bug：新增或更新 `docs/bug/` 记录。
- 有复用价值的大重构：新增或更新 `docs/refactors/` 记录。
- 构建、运行、部署、配置或验证变化：更新 `develop/` 和/或 `deploy/`。
- 开发/测试/生产真实环境、账号、数据库、缓存、队列、域名、部署拓扑、上线记录或回滚材料变化：更新 `.local/project-resources/` 对应环境；只有通用规则变化时才同步公开 `docs/`。
- 从需求到上线的执行流、脚本入口、门禁、确认策略或记录格式变化：更新 `AGENTS.md`、`docs/develop`、`docs/deploy` 和 `.local/project-resources/README.md`。
