# 项目文档规划器

## 目标

为项目创建完整、可复用的文档架构和开发规范基线。可以借鉴成熟项目的组织方式：目录职责、主文档、示例文档、模板、编号记录、索引习惯、维护矩阵和更新规则。不要复制参考项目的业务功能、模块名、产品范围、API 或实现细节。

当项目涉及开发、测试、生产、部署、上线、回滚、账号、密钥、数据库连接或第三方资源时，还要规划一个仓库外或 Git 忽略的私有项目资源层，让 AI 能在授权后按环境读取事实，而不是每次要求人工重新提供。

最终目标是让人只负责提需求和批准高风险动作；AI 负责按固定流水线完成计划、开发、验证、打包、测试环境发布、生产预检、上线、回滚准备和记录归档。

## 核心规则

每个保留的 docs 目录都必须包含：

- `README.md`：该目录的主入口文档。
- 一个示例文档：展示该目录下文档应如何书写。
- 可选模板或专题文档：只有对后续维护有帮助时才创建。

中文项目使用中文文件名。英文项目可以翻译为英文文件名，但要保持同样的文档角色。

`docs/` 只放可以提交的稳定规则、公开模板、通用部署说明和验收口径。真实服务器、域名、账号、密码、密钥、连接串、生产环境变量、上线流水、发版备份和事故操作记录应放在 `.local/project-resources/` 或项目指定的私有目录，并确保被 `.gitignore` 忽略。

## 参考项目抽象规则

当参考仓库已有成熟 docs 时，只抽象这些模式：

- 根目录 `docs/README.md` 不只是文件列表，还要说明文档目标、文档关系、更新规则、命名规范和首次阅读顺序。
- 公开 `docs/` 与私有 `.local/project-resources/` 分层：`docs/develop`、`docs/deploy` 写通用规则、模板和门禁；`.local/project-resources` 写当前开发/测试/生产的真实运行事实、凭据索引、数据库、部署拓扑、上线记录、回滚材料和 release 备份。
- `plans/`、`bug/`、`refactors/` 使用稳定且不复用的编号、模板、README 索引、状态字段、验证记录和交叉链接。
- 开发、测试、生产环境用 `dev/`、`test/`、`prod/` 分区。测试环境可以明确声明复用 dev，但必须写清实际 env、数据库、缓存/队列 namespace、隔离边界和未来拆分条件。
- 每个环境入口写当前有效文件、使用方式、禁止事项和风险边界。生产入口写部署方案、运维手册、发版记录、版本化 release、备份、回滚和旧数据离线迁移规则。
- 能自动化的安全边界不要只写在文档里：建议配套 env 加载脚本、打包脚本或部署脚本检查 dev/test/prod 隔离，拒绝把开发环境指向生产库、生产 Redis DB、生产 namespace 或生产密钥。
- 把常见人工指令映射为固定流水线：`开发需求`、`发测试`、`上线`、`回滚`、`查看生产问题`、`补发版记录` 分别指向计划模板、验证矩阵、环境资源、脚本入口和记录位置。
- 每条交付流水线都要有预检、执行、验证、失败处理和记录归档。生产上线默认需要明确确认；如果项目允许自动上线，必须写清预授权条件、时间窗口、自动回滚阈值和通知方式。
- 架构文档区分长期稳定边界和临时计划，并沉淀功能开发、问题修复、大文件重构等可复用指导。
- 前端文档可以拆分样式规范、响应式列表、通用组件边界、产品/品牌/运行时边界。
- 后端文档可以拆分分层边界、API/存储/schema 边界、后台任务、脚本、队列和运行时规则。
- 功能文档承载可长期维护的功能行为、接口契约、存储、安全、日志、权限和调研结论，不只服务某一个计划。
- 模板只保留一个权威版本；README 链接模板，不重复内嵌模板正文。

不要复制参考项目专属的菜单、供应商、模型、数据库名、命令、模块、问题记录或计划。无法确认的项目事实使用占位符、泛化示例或 `待确认`。

## 根目录 AGENTS.md 规则

如果项目有根目录 `AGENTS.md`，应抽象成可复用模板，而不是复制参考项目的具体事实。模板至少覆盖：

- 项目定位
- 工作原则
- 默认按当前最优方案开发，不主动向下兼容
- 通用规范入口
- 目录约定
- 私有项目资源目录与环境上下文
- AI 交付流水线与指令映射
- 模块边界
- 变更习惯
- 验证约定

## 默认开发策略

生成开发规范、`AGENTS.md` 模板或架构指导时，默认写入以下规则，除非用户明确要求兼容：

- 代码应朝当前最优模型、当前 schema、当前 API 契约和当前 UI 流程推进。
- 不为旧字段、旧请求结构、旧路由、旧表结构或旧 UI 流程在运行时代码中保留向下兼容。
- 不把双读、双写、启动迁移、临时同步、兼容兜底、迁移标记或一次性数据修复挂进正常 route、repository、worker、启动路径、前端页面或网关/请求路径。
- 如果必须处理既有数据，应记录为明确的离线 SQL、离线脚本或重建步骤。只有用户要求时才生成这类一次性路径，并且不保留为长期运行时代码。
- 如果项目已有契约、公开 API 或用户指令要求兼容，必须标记为例外，并写清兼容边界、退出条件和验证证据。
- 生成文档时，避免使用模糊的 `兼容策略`；改写为更清楚的 `当前 schema`、`默认值`、`离线处理边界`、`旧结构处理例外` 等表述。

## 探查流程

创建或规划文档前：

1. 阅读项目 `AGENTS.md`、`README*`、包管理清单、顶层目录和现有 `docs/`。
2. 如果存在 `.local/project-resources/`、`.local/`、`deploy/`、`.env.example`、环境加载脚本或发版目录，只读取结构、README、模板和脱敏说明；不要把真实密钥、连接串或 token 写入输出。
3. 识别项目定位、用户、技术栈、源码边界、部署目标、环境划分和当前规划需求。
4. 区分长期稳定架构、临时执行计划和私有运行事实。
5. 无法确认的事实标记为 `待确认`，不要编造产品细节、账号、域名、IP、数据库名或命令。
6. 判断项目是否有明确兼容义务；如果没有，应用“当前最优方案优先”的默认策略。
7. 按项目规模生成合适的 docs 树，但保留的每个 docs 目录都必须满足“主文档 + 示例文档”规则。
8. 对有多环境或上线需求的项目，同时生成或规划 `.local/project-resources/` 骨架，并确认 `.gitignore` 忽略该目录。
9. 识别项目已有脚本和命令，规划从需求到上线的固定流水线；缺少自动化入口时，用占位脚本名和待确认项记录，不编造已存在能力。

## 完整文档骨架

默认使用以下完整结构。只有用户要求缩小版本时才裁剪：

```text
docs/
├── README.md                         # 主文档：全局文档入口、目录索引、命名和维护规则
├── 文档架构示例.md                   # 示例：展示本项目文档如何组织
├── architecture/
│   ├── README.md                     # 主文档：架构类文档入口
│   ├── 架构总览.md                   # 主文档：项目定位、模块边界、关键流程

│   ├── 功能开发指导.md               # 规范：新增功能、字段、接口、存储、脚本、文档同步
```

## 私有项目资源骨架

当项目需要 AI 掌握开发、测试、上线和运维事实时，默认同时规划以下 Git 忽略目录。该目录不适用“每个目录必须有示例文档”规则，但每个环境入口和重要子目录应有 `README.md` 说明当前事实、使用方式、禁止事项和维护规则。

```text
.local/project-resources/
├── README.md                      # 私有资源总入口、环境分区、安全规则
├── dev/
│   ├── README.md                  # 开发环境当前事实和默认 Agent 上下文
│   ├── env/README.md              # 当前有效 env、加载方式、隔离边界
│   ├── accounts/README.md         # 开发账号或测试凭据索引
│   ├── database/README.md         # 开发数据库、缓存、队列、种子、重置
│   ├── logs/README.md             # 开发排障日志
│   ├── issues/README.md           # 开发中发现但未修复问题
│   └── runbooks/README.md         # 本地启动、重置、调试操作
├── test/
│   ├── README.md                  # 测试环境；无独立环境时声明复用 dev
│   └── env/README.md
└── prod/
    ├── README.md                  # 生产事实入口和操作门禁
    ├── env/README.md              # 生产 env、域名、端口；真实值以私有 env 为准
    ├── accounts/README.md         # 服务器、数据库、第三方账号索引
    ├── database/README.md         # 生产数据库、备份、恢复、离线迁移
    ├── deploy/README.md           # 真实部署拓扑、反代、守护进程、上线流程
    ├── logs/README.md             # 上线记录、事故日志
    ├── issues/README.md           # 生产已知问题
    ├── runbooks/README.md         # 回滚、恢复、证书、常用运维命令
    └── releases/
        ├── README.md              # 版本化发版备份规则
        ├── current-release.txt    # 当前线上版本指针
        └── YYYY-MM-DD_NNN/
            ├── artifacts/         # 发布包、二进制、静态产物
            ├── release.md         # 发版说明
            ├── checksums.txt      # 校验和
            └── rollback.md        # 回滚步骤
```

私有目录只保留当前项目事实和敏感材料，不复制到 `docs/`、聊天记录、截图、提交说明或发布包文档。公开文档可以链接或说明“真实值见私有资源目录”，但不写明文密钥和连接串。

## AI 一条龙交付流水线

为了减少人工接入，项目应维护“用户意图 -> 固定执行面”的映射。人只需要提出需求或发出上线指令，AI 先按文档读取上下文，再按脚本和 runbook 执行。

```text
需求提出
  -> 读取 AGENTS.md、docs/README.md、相关功能/架构文档
  -> 生成或更新 plans/计划-XXXX
  -> 开发实现与本地验证
  -> 发测试：加载 test/dev 环境、运行迁移和 smoke、记录验证
  -> 生产预检：读取 prod 私有资源、备份、检查 release 和回滚材料
  -> 上线：打包、部署、切换、健康检查、业务 smoke
  -> 归档：release.md、checksums.txt、rollback.md、logs、current-release
```

推荐在 `AGENTS.md` 或 `.local/project-resources/README.md` 写清：

| 用户说法 | AI 默认动作 | 需要人工确认 |
| --- | --- | --- |
| “开发/实现/修复 X” | 创建计划、改代码、跑本地验证、更新 docs/bug/refactors | 否，除非需求不清 |
| “发测试/部署测试环境” | 加载 test 或 dev 隔离环境、执行 migration/smoke、记录测试发布 | 通常否 |
| “上线/发生产” | 生产预检、生成 release、备份、展示上线摘要 | 是，默认必须明确确认 |
| “回滚” | 读取 current release 和 rollback.md，展示回滚目标与数据影响 | 是，除非项目预授权自动回滚 |
| “排查线上问题” | 读取 prod runbook 和 logs，只执行只读诊断 | 写操作需要确认 |

每条流水线应写清入口文档、自动化脚本、成功证据、失败处理和记录位置。推荐脚本入口包括 load-env、preflight、test、build、package、deploy、smoke、rollback、release-log。

## 目录职责

- `docs/`：全局文档地图、命名规范、更新规则和 AI/维护者阅读顺序。
- `architecture/`：稳定项目边界、技术方向，以及功能开发、问题修复、重构等长期规则。
- `architecture/frontend/`：前端信息架构、布局、样式、交互、响应式列表、通用组件、文案和品牌/运行时边界。
- `architecture/backend/`：服务边界、API 分层、存储访问、后台任务、队列、脚本、中间件和集成边界。
- `functions/`：功能级行为、流程、字段、状态、权限、契约、安全和日志专题。
- `plans/`：临时执行计划、编号任务、里程碑、范围决策和验收标准。
- `develop/`：本地安装、启动、测试、验证、夹具和排障。
- `deploy/`：构建、发布包、环境变量、目标运行时、启动、健康检查和回滚。
- `.local/project-resources/`：Git 忽略的私有环境上下文，按 dev/test/prod 保存 env、账号、数据库、部署拓扑、上线记录、运维手册、release 备份和回滚材料。
- AI 交付流水线：把需求、开发、测试发布、生产预检、上线、回滚和事故排查映射到固定文档、脚本和记录位置。
- `bug/`：可复现问题、根因、修复、验证、复发预防和历史关联。
- `refactors/`：大文件拆分、模块抽取、重复逻辑收敛、验证和可复用经验。

## AGENTS.md 模式

为新项目设计 agent 指令时，包含：

- 项目定位和当前边界。
- 工作原则，尤其是边界变化前先更新文档，以及默认按当前最优方案开发。
- 源码目录约定。
- docs 目录约定和必读入口。
- `.local/project-resources/` 约定：Agent 默认读取 dev；test 复用 dev 时必须明示；生产操作前必须切换到 prod 上下文并获得明确确认；真实凭据只放私有目录。
- 用户意图映射：开发、发测试、上线、回滚、线上排查分别走哪些文档、脚本、环境和记录位置。
- 使用当前项目事实描述模块边界，不复制参考项目示例。
- 新字段、API、存储、脚本、UI、部署、问题和重构的变更习惯。
- 明确“不默认向下兼容”：除非用户明确要求，否则不保留运行时兼容分支或旧 schema/API 兜底。
- 兼容例外处理：记录范围、来源约束、退出条件和验证证据。

## 输出格式

当用户要求设计文档架构时，返回或创建：

- `【文档架构】`：完整目录树，确保每个目录都有 `README.md` 和示例文档。
- `【私有资源目录】`：`.local/project-resources/` 或等价私有目录树、环境分区、Git 忽略规则和安全边界。
- `【交付流水线】`：从需求到上线的用户意图映射、自动化脚本入口、预检、验证、回滚和记录归档。
- `【目录职责】`：每个目录的用途和应放内容。
- `【首批文件】`：优先创建的主文档、示例和模板。
- `【维护规则】`：功能、API、存储、UI、环境、部署、上线、问题和重构变化时需要更新哪些公开文档和私有资源。
- `【开发规范】`：当前最优方案默认规则、不向下兼容规则、离线数据处理边界、分层、验证和例外策略。
- `【环境上下文】`：dev/test/prod 默认读取顺序、当前有效 env、隔离校验、生产操作门禁、发版备份和回滚记录要求。
- `【待确认】`：需要产品或技术确认的假设。
- `【AGENTS模板】`：可复用的根目录 `AGENTS.md` 骨架，带项目规则和占位符。

如果直接编辑文件，生成的文档要简洁，使用相对 Markdown 链接，并避免复制任何参考仓库的产品专属内容。
