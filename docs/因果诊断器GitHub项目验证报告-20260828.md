# 因果诊断器 GitHub 项目验证报告

## 结论

本轮对三个真实 GitHub 修复前提交运行了已安装的 `causal-debugger`。结果支持一个有边界的判断：

- CodeGraph 能在秒级建立并读取全局结构索引；本轮三例的 MCP 分析返回耗时约 `176-263 ms`。
- 加入错误堆栈或日志中的源代码位置后，因果分析可以把候选根因收敛到实际修复函数或文件，并保留多个候选及反事实字段。
- 没有运行时位置时，静态调用邻近关系可能把调用方或同文件其他函数排在真正根因前面；因此不能宣称“只靠图就能找全根因”。
- 本轮是可复核 Spike，不是正式 Gate。样本只有 3 个仓库、每个 1 个 Bug、1 次重复，没有统计意义上的普遍提速结论。

在 `CLIProxyAPI` 中只用符号查询而不提供运行时错误位置时，早先结果把 `buildCodexClientModels` 排在第一根因；加入 `codex_client_models.go:197` 后，第一候选变为真实修复函数 `applyCodexClientSearchToolSupport`。这是本轮最直接的证据：源位置、错误码、trace/span 等运行时证据是因果排序的关键输入。

## 上游回归测试

- `chi` 修复提交新增的 `TestMountingSelf` 在 fixed 快照上通过，包含 direct self-mount 和共享 tree 的 inline mux 两个子测试。
- 同一测试名在 parent 快照上显示 `no tests to run`，说明该回归测试确实由修复提交引入；parent 的其他 `go test ./...` 仍可通过，符合“旧代码不一定有已有测试覆盖该 Bug”的情况。
- `click` parent/fixed 均能在本机 Python `3.11` 导入。机器没有 Python `3.10`，因此没有声称重现 Python 3.10 的原始 `TypeError`；该案例的真值来自 GitHub 修复 diff，运行时复现项明确标记为未验证。

## 对预期目标的回答

本轮证明了“让 AI 一次看到更多相关内容”有实际价值：三例都在一次本地分析中返回索引规模、多个种子、关系子图、多个候选根因和反事实字段；在带源位置的情况下，根因可以直接收敛到修复文件/函数，减少模型反复 grep 的需要。

本轮没有证明以下更强结论：

- 模糊自然语言可以稳定召回全部相关节点；
- 静态调用图可以代替真实因果或跨服务 trace；
- 每个项目都能减少到两次模型调用；
- 已达到生产级插件或正式 Gate。

## 下一步

继续做是有价值的，但实现重点应放在证据编排，而不是继续堆叠静态打分：

1. 保留 CodeGraph 作为结构召回层，固定 source/target/kind/relationId 的可审计身份。
2. 把错误堆栈、日志、trace/span、配置键和失败测试统一映射为运行时证据；映射失败必须输出 `unknown`。
3. 增加跨语言和跨服务样本，并用至少 20 个 Bug、3 个仓库、6 类别、每例 3 次重复验证 Top-3、关键关系召回、定位时间、输入 token 和高置信误判率。
4. 模型只负责解释、排序和提出最小补查；不要让模型重新扫描整个仓库。
