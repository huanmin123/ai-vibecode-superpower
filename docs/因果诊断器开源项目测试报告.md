# 因果诊断器开源项目测试报告

## 结论

本轮验证支持“值得继续做，但必须先做证据编排层”的判断：CodeGraph 公共 SDK 可以在秒级以内提供稳定的全局结构切片，因果引擎可以在本地毫秒级完成多假设路径枚举，RTK 可以在进入模型前压缩和脱敏日志。它们确实能让 AI 一次看到更多相关上下文。

但当前原型还不能证明“自动找全根因”或“所有项目都大幅提速”。在没有运行时证据、症状到代码节点的可靠映射、跨服务边界和固定回归集时，静态调用图会把邻近节点误排为根因。因此正式插件仍处于 No-Go；当前可交付边界是可复现 Spike，而不是生产级 MCP 插件。

## 实测环境与方法

- CodeGraph `1.5.0`，通过公开 npm SDK `CodeGraph.open(..., { readOnly: true })` 读取，不访问私有 SQLite。
- RTK `0.44.1`，用于有界读取、去重/压缩、脱敏和来源哈希保留；RTK 不负责因果判断。
- 本地因果引擎使用有界 reverse Beam Search，默认 `maxDepth=3`、`beamWidth=24`；所有候选保留分数、路径和反事实独立覆盖率。
- 测试命令：

```powershell
Set-Location F:\ai-vibecode-superpower\experiments\causal-debugger-benchmark
npm.cmd run check
npm.cmd test
```

结果：`24/24` 测试通过。

现已提供可复现入口 `npm.cmd run analyze`。例如：

```powershell
npm.cmd run analyze -- --project <project-dir> --query <symptom-or-symbol> --max-depth 3 --limit 250 --out <analysis.json>
```

本轮两个快照均通过该入口生成分析 JSON；CLIProxyAPI 输出 5 个节点/7 条边，fast-boot 输出 19 个节点/22 条边。

另外在 CLIProxyAPI 快照上注入一条带 `sdk/api/handlers/openai/codex_client_models.go:200:1` 的错误观测，适配器成功映射 `1` 个运行时事件、产生 `1` 个 `event` 观测节点，因果排序的第一候选变为实际报错函数节点；无效路径则进入 `unknown`，不会绑定到邻近函数。

## 开源项目结构切片测试

| 项目快照 | 语言/文件 | CodeGraph 节点/边 | 查询到种子 | 有界切片节点/边 | 证据准备耗时 |
|---|---:|---:|---:|---:|---:|
| CLIProxyAPI，`holdout-cliproxy-tool-search-template-v1` | Go 770 / 811 | 17,972 / 67,244 | 1 | 10 / 13 | 约 155 ms |
| fast-boot，`holdout-fastboot-validation-groups` | Java 489 / 510 | 7,691 / 13,245 | 1 | 25 / 34 | 约 17 ms |

两份索引均为 `state=complete`、`stale=false`、`pendingReferences=0`。这证明“先由代码建立全局结构，再交给 AI”在本地运行时是可行的，并且不会随着整个仓库规模线性把全部代码塞进上下文；发送给模型的是受边界控制的关系子图。

### 重要失败证据

在 CLIProxyAPI 的真实问题中，查询种子为 `applyCodexClientSearchToolSupport`。静态图能够在约 155 ms 找到该函数及其上游关系，但当前实验引擎在没有日志/测试结果作为运行时证据时，把 `buildCodexClientModels` 排在第一根因，真实修复关系是 `relation.codex-search.requires-template`。这不是实现“坏了”，而是明确暴露了当前边界：调用图邻近性不能替代因果证据。

因此必须把以下内容作为输入，而不是让模型自行猜：失败日志中的错误码/traceId、复现测试结果、变更 diff、已知排除项，以及冻结的关键关系 ID。

## AI A/B 证据（已有真实 Spike）

### fast-boot 单案例

已有 `fastboot-validation-groups` Spike 中，baseline 与 assisted 都命中 Top-1，但样本只有 1 个，不能作为普遍结论：

- 首个正确根因时间：`98,254 ms → 20,570 ms`，下降约 `79.1%`。
- P75 输入 token：`303,551 → 22,928`，下降约 `92.4%`。
- assisted 证据准备 P95：`311 ms`。
- 关键关系召回：`1.0`，但该案例仅有 1 条关键关系。

### CLIProxyAPI 单案例

`cliproxy-tool-search-template` Spike 中，assisted 在约 `59.9 s` 完成、未调用工具，Top-1 根因命中；baseline 在 `180 s` 超时且没有 provider usage。由于 baseline 不完整，评估结果为 `insufficient_data`，不能把这次差值宣传为提速结论。

## 日志/控制台压缩验证

`runtime-evidence.mjs` 已实现：

1. 有界流式读取（最大字节数、行数和压缩字符数）；
2. 调用已安装的 `rtk.exe log`；
3. 保留原始日志 SHA-256、读取边界和截断标记；
4. 脱敏 `Authorization`、`Bearer`、cookie、token、password、secret、API key 和连接串；
5. RTK 失败返回 `status=failed` 与原始错误，不伪造压缩成功。

这能降低模型输入噪声和 token，但“压缩后是否仍保留足以判根因的证据”仍需在多项目日志集上做召回测试。

## 是否达到预期

已经达到的预期：

- 代码在本地快速构建全局关系上下文；
- 一次请求可携带多条候选链路、证据引用和边界信息；
- 支持多假设、置信度和反事实字段；
- 日志在进入模型前可压缩、脱敏并保留来源可追溯性；
- 发现了“静态邻近关系误当根因”的真实失败模式，避免过早产品化。

尚未达到的预期：

- 不能保证模糊问题自动召回全部相关节点；
- 不能仅凭 CodeGraph 调用/引用边判断真实因果；
- 尚无满足正式 Gate 的多仓库、多类别、多次重复样本；
- 还没有完成 MCP/skill 的生产级封装。

## 建议的下一阶段

1. 固定至少 20 个 holdout bug、3 个以上真实仓库、6 类故障、每例至少 3 次重复，并冻结 `relationId`。
2. 增加“症状 → 节点”证据适配：错误堆栈、测试失败位置、trace/span、配置键和 diff 必须能映射到图节点；映射失败要显式报告未知。
3. 用 CodeGraph 只做结构召回，用运行时证据和干预/反事实结果做因果打分；模型只负责解释、排序和提出下一项最小验证，不负责全仓库盲搜。
4. 以以下 Gate 作为是否进入插件实现的门槛：Top-3 ≥ 80%，关键关系召回 ≥ 85%，中位定位时间下降 ≥ 30%，P75 输入 token 下降 ≥ 40%，高置信错误率不升，固定回归无误报。

当前决策：继续投资“证据包 + 因果引擎”Spike；暂缓完整插件发布，直到上述 Gate 在独立 holdout 上通过。

## 插件当前状态

已新增 `plugins/causal-debugger` 只读第一版，包含 `causal_status` 和 `causal_analyze` 两个 MCP 工具，并将因果引擎、CodeGraph 适配器和 RTK 运行时证据模块打包到插件目录。插件 manifest 校验通过，MCP 协议测试 `2/2` 通过，且已在 fast-boot 快照上端到端返回 `state=complete`、`7,691` 个 CodeGraph 节点、`19` 个分析节点和 `22` 条分析边。

该只读第一版已由 `install-codex.ps1` 与 `install-codex.sh` 接入自动部署，并在本地 marketplace 登记为 `AVAILABLE`。这不等于正式 Gate 已通过：完整性、跨服务归因和大样本 A/B 证据仍是后续放行条件。

安装契约已用隔离的 fake Codex CLI 验证：PowerShell 流程会先安装 `agnets-workflow`，再安装 `causal-debugger`，两者的缓存、版本、启用状态和 marketplace 注册均被断言；插件自身 `npm.cmd test` 为 `2/2`，`npm.cmd run check` 通过，benchmark 回归为 `25/25`。完整 `agnets-workflow` 回归当前为 `128/129`，唯一失败是既有 Windows 8.3 路径大小写断言，与本次插件接入无关，单独复跑仍稳定复现。
